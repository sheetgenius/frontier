# Patched for Whom

On June 24 and again on June 26, OpenHands tagged the dependency-CVE fixes it had
been sitting on:
[cloud-1.39.0](https://github.com/OpenHands/OpenHands/releases/tag/cloud-1.39.0)
and [cloud-1.40.0](https://github.com/OpenHands/OpenHands/releases/tag/cloud-1.40.0).
Both are cloud tags. The open-source line got nothing. Its newest release is
still [1.8.0](https://github.com/OpenHands/OpenHands/tags), from June 10.

After cloud-1.40.0 a fresh
[authlib CVE](https://nvd.nist.gov/vuln/detail/CVE-2026-44681) landed on `main`
([commit e6fe505](https://github.com/OpenHands/OpenHands/commit/e6fe505)),
untagged: an unauthenticated open redirect in the OIDC flow, the kind used to
bounce a victim through a trusted domain into a phishing page.

So a managed OpenHands Cloud tenant is patched. A self-hoster pinned to 1.8.0 is
not, and has no open-source tag to move to. For three issues the gap was between
merged and shipped. Here it became cloud versus self-host, which is a billing
boundary.

The fix itself is not the story. Almost every project on the watchlist closed the
same class of gap this window: places where an agent's own inputs could escalate
past the boundary, whether a model-chosen ID, an injected command, a
self-approved config or a runaway subagent. Then the field split on who gets the
fix, and the answer now depends on which channel you run.

## The fix went everywhere except the tag

Hermes ran the other extreme from OpenHands: everything, nowhere. A
[path-traversal fix](https://github.com/NousResearch/hermes-agent/pull/55929) for
model-supplied tool-call IDs that could escape the tool-result directory, a
[command-approval-bypass close](https://github.com/NousResearch/hermes-agent/pull/55959),
and [secret redaction](https://github.com/NousResearch/hermes-agent/pull/55955) in
approval prompts all landed on `main`.

The bypass is the one to remember. GNU long-flag abbreviations of
`chown --recursive` and `git push --force` had been slipping past the guard. The
newest tag is still v2026.6.19, so if you run it, a rule you believed blocked
`chown --recursive` can be beaten by typing `--rec`.

Gemini's open-source repo split within itself. The skill path-traversal fix,
stranded in preview for two windows,
[reached stable in v0.49.0](https://github.com/google-gemini/gemini-cli/releases/tag/v0.49.0)
on June 25, while newer `@file` path hardening
([commit b5fc06e](https://github.com/google-gemini/gemini-cli/commit/b5fc06e))
stayed on `main`.

And Codex cut four stable 0.142.x patches while
[0.143.0 held alpha-only](https://github.com/openai/codex/compare/rust-v0.142.4...rust-v0.143.0-alpha.31)
through alpha.31. The OTEL and Codex Apps MCP work is real, and it shipped to no
one.

The question an operator actually has is whether the fix is in the thing they
run. This week the answer depended on whose thing it was.

## Google retired the CLI you could read

On June 18, 2026, [Google stopped serving requests](https://developers.googleblog.com/an-important-update-transitioning-gemini-cli-to-antigravity-cli/)
to consumer Gemini CLI: Google AI Pro and Ultra, free individual Code Assist,
and new GitHub-organization installs. Enterprise Code Assist kept access. The
open-source `gemini-cli` repository stays Apache-2.0 and enterprise-serving. The
consumer path is now [Antigravity CLI](https://github.com/google-antigravity/antigravity-cli/releases),
the `agy` binary: a closed-source Go rewrite.

Outside the vendor it read as one more entry in a familiar sequence,
[[q:greenland-105k-stars]], with Redis, HashiCorp and Elastic named in the same
breath.

The shutdown is not the lead. The trade it forces is. Gemini CLI was open: an
approval rule or a sandbox boundary was, in principle, readable. Antigravity is
not, and in a single release train its governance moved in both directions.
[1.0.13](https://github.com/google-antigravity/antigravity-cli/blob/main/CHANGELOG.md)
(June 27) *hardened* command permissions: "Always Approve" rule matching is now
strict and non-regex by default, closing a class of over-broad approve rules.
Three days later,
[1.0.14](https://github.com/google-antigravity/antigravity-cli/blob/main/CHANGELOG.md)
(June 30) *loosened* them, adding an "always proceeds" mode that auto-approves a
subagent's artifacts, work the parent flow never confirmed.

Both changes are quoted from a changelog. Neither can be checked against the
code, because there is no code to check. For the tier that just got migrated,
the authority layer did not weaken or strengthen. It became unauditable. The
[Antigravity profile](/profiles/antigravity/) holds the full read; the
[Gemini CLI profile](/profiles/gemini-cli/) holds the other side.

## An unverified report, and a company that acted on it

On June 30 a report circulated claiming Claude Code carried hidden code that
detects users on China-linked routes and injects signals about them into the
prompt. Within hours tinygrad posted that
[[q:tinygrad-ban]]. Aggregator accounts carried the claim onward the same day.

We cannot tell you whether the report is right. We read the Claude Code
changelog across v2.1.190 to v2.1.200 and found telemetry work (double-count
fixes, an opt-in OpenTelemetry response log) and nothing matching the described
behaviour. The report itself does not resolve from any source we hold. Anthropic's
restriction on China-linked access is public and predates all of this. So the
substance stays unestablished here, and none of it is a finding.

What is checkable is the shape of the week. An enterprise removed a coding agent
from its systems and urged others to do the same, on the strength of a document
most people sharing the story had not read. It is the same problem as the rest
of this issue, pointed the other way: a claim about a control, travelling faster
than anyone's ability to check it.

## Where the hardening did reach the operator

Where controls did ship stable, they got more specific and better aimed.

[Claude Code 2.1.196](https://github.com/anthropics/claude-code/releases/tag/v2.1.196)
is a security release worth the upgrade. `claude mcp list` and `get` no longer
spawn `.mcp.json` servers that a repository self-approves, so merely inspecting
MCP config in an untrusted repo can no longer launch a server the repo declared.
Remote Control is now disabled when `ANTHROPIC_BASE_URL` points at a
non-Anthropic host.

[Codex 0.142.2](https://github.com/openai/codex/pull/24092) gates PowerShell whose
AST regions the classifier cannot inspect behind approval rather than running it,
and switches MCP tool discovery to
[tool-search by default](https://github.com/openai/codex/pull/29486).

[Paperclip v2026.626.0](https://github.com/paperclipai/paperclip/releases/tag/v2026.626.0)
finally tagged 128 commits of master-only control plane: hard daily run-count and
cost ceilings enforced before an adapter runs, and a
[`skills:create` permission](https://github.com/paperclipai/paperclip/pull/8616)
split out from `agents:create`. [OpenClaw](https://github.com/openclaw/openclaw/releases/tag/v2026.6.11)
shipped `/fast auto` and approval-tool hardening to stable, with a
channel-owner-only approval-scope fix still on main.

## A new model spread in a week, and the platform held

Two threads run under all this. The first is capability. **Sonnet 5 propagated
in a week.** [Claude Code 2.1.197](https://github.com/anthropics/claude-code/releases/tag/v2.1.197)
made it the default with native 1M-token context, and
[Pi 0.80.3](https://github.com/earendil-works/pi/releases/tag/v0.80.3) added
support the same week. A new frontier model became a default and a cross-harness
option within days. If you pin models, that default changed under you.

The second cuts against everything above.
[eve](https://github.com/vercel/eve), durability-first and
human-in-the-loop-first, spent the window making its governance *more*
first-class: it
[repaired its approval-resume contract](https://github.com/vercel/eve/pull/424)
so a plain "approve" reply resolves a pending tool approval, and
[capped recursive subagent delegation](https://github.com/vercel/eve/pull/409) at
depth three with model-visible guards.

Where the self-hostable harnesses shipped their governance fixes to main but not
to a tag, the platform-hosted one shipped containment to its runtime. The axis
from *[Governance, Sold Separately](/digests/2026-06-23_2026-06-24-weekly/)*
holds: govern it yourself on your host, or govern it durably on a platform. This
window, the platform side was the one whose controls you could actually run.

## Provider notes

Everything else that moved is above. Three notes remain.

- **[Hermes](/profiles/hermes-agent/)** tagged none of its security wave, and on
  June 30 announced that [[q:hermes-web-60x]]. The capability got a number and a
  post. The containment got neither.
- **[Paperclip](/profiles/paperclip/)** led its own announcement of the
  control-plane release with [[q:paperclip-hermes-built-in]], not with the
  budget ceilings, which are the part an operator should wire first.
- **[Agent Zero](/profiles/agent-zero/)** `v2.0/v2.1` bumped LiteLLM past
  [CVE-2026-42271](https://nvd.nist.gov/vuln/detail/CVE-2026-42271), an
  exploited command-injection chain that can leak every provider key the proxy
  holds. Below v2.0, upgrade.

[Flue](/profiles/flue/) iterated durability primitives on preview only, and
[heypi](/profiles/heypi/) held at 0.2.0 beta.

## Whose fix is it

Every provider on this watchlist hardened something this window. Then it split
four ways on who receives the hardening. Cloud but not self-hosted. Main but not
tagged. Stable but not the substance. And for Gemini's consumers, a service retired
entirely, with the replacement unreadable.

The question stopped being whether a fix exists. Almost all of them do. The
question is whether it is for you, and that is now decided by which channel you
happen to run.
