# Governance, Sold Separately

heypi's headline feature is approvals. Its own
[approvals page](https://heypi.dev/docs/configuration/approvals) contains the
sentence that walks the headline back: *approval does not make every tool call
require approval. Tool confirmation does that.* Out of the box, the only
automatic gate is a bash command classifier that blocks destructive commands and
pauses on risky ones. Every other tool runs ungated until an operator wires a
policy by hand.

That is documented, not concealed. It also means a team that adopts heypi *for*
its approvals is buying a kit, not a posture.

[heypi](https://heypi.dev/) joins the watchlist this window. It is a TypeScript
framework for one agent a whole team uses in Slack, Discord and Telegram, with
approvals, an audit record, sandboxed tools and encrypted secret handoff. What
makes it worth the space is what it is built on. It pins
[Pi](https://pi.dev/) as a hard dependency, and Pi is the harness that has made a
principle of refusing to govern: no permission popups, no plan mode, build your
own confirmation flow. heypi is that confirmation flow, sold as a product. The
agent loop is the commodity underneath. The authority around it is the thing you
buy. A builder on the Flue side of the same problem replied to the launch:
[[q:barba-converge]]

## The real defaults are the quiet ones

The landing page promises *a multiplayer chat agent for your team* with
*approvals, an audit trail, and sandboxed tools*. The docs describe something
more modest and more useful: governance primitives with conservative defaults,
where the headline controls are things you assemble.

The conservatism lives where nobody demos it. The default
[runtime](https://heypi.dev/docs/configuration/runtime) is an in-process bash
interpreter over a virtual filesystem with the network off. The
[admin panel](https://heypi.dev/docs/configuration/admin), which is also where
the advertised audit trail lives, as typed trace events rather than a ledger, is
off by default, binds to loopback, and hands out a one-time login URL that
expires in five minutes. Memory is off. The docs say of the admin setting:
*never set it on a public host*.

heypi is at its best when it states a limit. The
[secret handoff](https://heypi.dev/docs/configuration/secrets) encrypts a
credential in the browser so it never enters chat history or the model context,
then tells you the secret rests as a readable file in the runtime workspace. The
encryption protects the handoff, not the storage. It
[does not replay](https://heypi.dev/) an in-flight turn after a crash, and says
so. A Show HN commenter named the value: most frameworks
[forget the human-in-the-loop part](https://news.ycombinator.com/item?id=48327336),
*critical for anything with real side-effects*. heypi remembers it, then leaves
it switched off until you reach for the switch.

The
[0.2.0-beta.0](https://raw.githubusercontent.com/hunvreus/heypi/0.2.0-beta.0/CHANGELOG.md)
tag (23 June) tightened things further. Webhooks are HTTPS by default, and a
misplaced root-level approver block now fails at startup instead of silently not
binding. It is a beta, heypi cuts
[no GitHub releases](https://github.com/hunvreus/heypi/tags), only tags, and two
dozen commits already sit on `main` past it.

## heypi against its neighbours

Against Pi, heypi is the layer Pi told you to build, not a competitor. Against
[OpenClaw](https://docs.openclaw.ai/), which it was first described as a version
of (*Openclaw, but for teams*), it trades a single-user gateway for a multiplayer
one, with approver and admin identities scoped per chat adapter rather than per
sender.

The comparison that changes a decision is [eve](https://github.com/vercel/eve).
Both document their governance. heypi ships approvals off and disclaims crash
replay. eve's [human-in-the-loop docs](https://eve.dev/docs/human-in-the-loop)
make approval gates and a pause-for-a-human tool first-class, and its durable
runtime resumes the paused turn after a crash. heypi is an app you run on your own
host; eve is an agent that lives on a managed runtime. If an in-flight turn must
survive a crash, that difference decides it. The fuller comparison is in the
[heypi profile](/profiles/heypi/).

## A boundary, withdrawn in public

Hermes cut no tag in these two days, but it held a governance argument in the
open. On 22 June a
[commit](https://github.com/NousResearch/hermes-agent/commit/8845f3316) on
`main` stopped the dashboard auto-importing the Python backends of
user-installed plugins, reserving backend routes for bundled ones. It was part
of the security wave *Protected on Paper* covered. A plugin author found it on
the 24th, tagged the lead, and wrote: [[q:8bit64k-plugin-contracts]]

The lead replied within half an hour that it was a mistaken change being
reverted, and why: [[q:teknium-mistaken-change]]

Set that against the record and it is a real position, not a shrug. The same
wave answered a campaign that, by the project's own commits, found exposed
dashboards. His answer holds that line at the operator's network, not in the
plugin API, and keeps the extension contract whole. We hold no receipt
for the revert inside the window; it is his statement. It is also the opposite
of heypi's bet. heypi sells the boundary. Hermes hands it back to you.

## Somebody else's refusal

A harness that refuses to govern points upward. A framework whose whole product
is the governance layer ships its headline control switched off. Between them
sits an operator who now buys the ability to say no separately from the thing
that acts.

The argument reached past heypi the same day. Ashwin Gopinath, the day after
Anthropic launched Claude Tag in Slack, called it useful and argued that the
lock-in to worry about is context, not the model:
[[q:ashwingop-own-the-context]] And Simon Willison, whose prompts in Claude Code
for web mostly start by cloning a repo, showed what a refusal feels like from
the receiving end. He reported that [[q:simonw-egress-blocked]] and asked
whether it was a known issue. He had not written that policy.

Buying it separately is not obviously wrong. Specialisation usually beats one
vendor doing everything badly. But it changes what you are purchasing. You are not buying a
boundary. You are buying somebody else's promise to hold one, kept on somebody
else's week.
