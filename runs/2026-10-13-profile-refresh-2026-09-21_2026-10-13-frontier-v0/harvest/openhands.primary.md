## 1. v1.25.0 stops serving the session key to the network; npm, desktop and Docker installs before it exposed the key to anyone who could reach port 8000

- **Date:** 2026-10-06
- **Channel:** `tagged-release`
- **Ancestry evidence:** #17007 merge c5efa3ae41 (merged 2026-09-29T00:47:28Z) is an ancestor of v1.25.0 and not of v1.24.0 (`git merge-base --is-ancestor`). Before, at v1.24.0: ingress `server.listen(config.port, ...)` with no host ([ingress.mjs L226](https://github.com/OpenHands/OpenHands/blob/v1.24.0/scripts/ingress.mjs#L226)); static server default `host: "::"` ([static-server.mjs L89](https://github.com/OpenHands/OpenHands/blob/v1.24.0/scripts/static-server.mjs#L89)); Docker entrypoint `--host ::` plus `--session-api-key` ([entrypoint.sh L395-L398](https://github.com/OpenHands/OpenHands/blob/v1.24.0/docker/entrypoint.sh#L395-L398)); Docker quickstart `-p 8000:8000` ([README L96](https://github.com/OpenHands/OpenHands/blob/v1.24.0/README.md#L96)). The desktop app runs the same launcher (`electron/main.mjs` imports `dev-with-automation.mjs` with `staticMode: true` at v1.24.0). After, at v1.27.1: `DEFAULT_BIND_HOST = "127.0.0.1"` and `applySessionKeyPolicy` ([bind-host.mjs L8-L77](https://github.com/OpenHands/OpenHands/blob/v1.27.1/scripts/bind-host.mjs#L8-L77)); Docker opt-in ([entrypoint.sh L413-L416](https://github.com/OpenHands/OpenHands/blob/v1.27.1/docker/entrypoint.sh#L413-L416)); Docker conversation runtime binds 0.0.0.0 ([dev-with-automation.mjs L494-L498](https://github.com/OpenHands/OpenHands/blob/v1.27.1/scripts/dev-with-automation.mjs#L494-L498)).
- **Receipt:** https://github.com/OpenHands/OpenHands/releases/tag/v1.25.0, https://github.com/OpenHands/OpenHands/pull/17007, https://github.com/OpenHands/OpenHands/issues/16879, https://github.com/OpenHands/OpenHands/blob/v1.27.1/scripts/bind-host.mjs#L8-L77, https://github.com/OpenHands/OpenHands/blob/v1.24.0/docker/entrypoint.sh#L395-L398, https://github.com/OpenHands/OpenHands/blob/v1.27.1/README.md#L142-L144, https://github.com/OpenHands/docs/blob/9daa7e5b5cd49453ce0f571810859a747eab5334/openhands/usage/agent-canvas/release-notes/v1.25.0.mdx
- **Half:** both | **Confidence:** high (code read at both tags; the exposure itself not reproduced here)

**What changed.** Through v1.24.0 the npm `agent-canvas` launcher and the desktop app started the port-8000 ingress on every interface and the static server on `::`, with the stack's session API key written into the served HTML; the Docker image did the same, and its README quickstart published `-p 8000:8000`. Anyone who could reach the port could read the key and use it on the proxied agent-server and automation APIs. The report ([#16879](https://github.com/OpenHands/OpenHands/issues/16879)) was public with reproduction steps from 2026-08-24 and reproduced on v1.16.0. The fixed release shipped 43 days later. v1.25.0 binds npm and desktop listeners to 127.0.0.1 by default, refuses to inject the key when a listener is off loopback (the UI falls back to the API-key prompt used by `--public`), keeps the Docker image key-free unless `AGENT_CANVAS_ALLOW_LAN_SESSION_KEY=true`, and rewrites the Docker quickstart to publish on 127.0.0.1 with that opt-in. With `OH_CONVERSATION_RUNTIME=docker` the launcher deliberately binds the key-free stack to 0.0.0.0 so conversation containers can reach it through host.docker.internal. No advisory was filed, and the docs site's v1.25.0 release notes mention neither the fix nor the Docker behavior change.

**Operator consequence.** Run v1.25.0 or later (v1.27.1). If you ran v1.24.0 or earlier through npm, the desktop app, or Docker published beyond loopback on a network others could reach, treat the session key as exposed: plan session-key rotation together with encrypted automation-state migration (the automation KV secret is derived from the key unless `AUTOMATION_KV_SECRET` is set), then review saved secrets, automations and recent conversations for activity you did not start. On Docker, do not rotate by setting `LOCAL_BACKEND_API_KEY` alone (section 2). After upgrading, an API-key prompt on a Docker quickstart without the new flags is the fix working. In per-conversation Docker mode, firewall port 8000, because the stack listens on every interface behind the key. Human attention: with no advisories, the ordinary PR and release diff, rather than an advisory alert, carry this warning.

## 2. Docker image: setting LOCAL_BACKEND_API_KEY leaves the agent server with no key at all (open #17763, unfixed at v1.27.1 and on main)

- **Date:** 2026-09-28
- **Channel:** `tagged-release`
- **Ancestry evidence:** The defect ships in every tag from v1.20.0 to v1.27.1: the same block is at [v1.20.0 entrypoint.sh L200-L211](https://github.com/OpenHands/OpenHands/blob/v1.20.0/docker/entrypoint.sh#L200-L211) and [v1.27.1 L208-L219](https://github.com/OpenHands/OpenHands/blob/v1.27.1/docker/entrypoint.sh#L208-L219), and a `git diff` of docker/entrypoint.sh between v1.27.1 and the closing main SHA (0e9ce191390f535347ff17055038c45eeef3fedf) is empty. `git log -L` dates the block to 14b1b1e8a (2026-06-01, "two auth modes"). README.windows.md L32 arrived with #17007 (first in v1.25.0).
- **Receipt:** https://github.com/OpenHands/OpenHands/issues/17763, https://github.com/OpenHands/OpenHands/blob/v1.27.1/docker/entrypoint.sh#L208-L219, https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/config.py#L227-L237, https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/dependencies.py#L25-L37, https://github.com/OpenHands/OpenHands/blob/v1.27.1/README.windows.md#L32, https://github.com/OpenHands/OpenHands/blob/v1.27.1/docker/entrypoint.sh#L427, https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/api.py#L456-L523
- **Half:** defect | **Confidence:** high on the code path; medium on end-to-end effect (not probed here; the vendor's AI triage on the issue says it verified the defect against main)

**What changed.** In the all-in-one Docker image, entrypoint.sh exports `OH_SESSION_API_KEYS_0` only inside the branch that runs when neither `LOCAL_BACKEND_API_KEY` nor `OH_SESSION_API_KEYS_0` is set. The agent server reads only `OH_SESSION_API_KEYS_0` or `SESSION_API_KEY` ([config.py L34-L45](https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/config.py#L34-L45)), its own field doc says "Empty list implies the server will be unsecured", and `check_session_api_key` passes every request when the list is empty. The static server in front routes `/api` to the agent server without checking the key itself ([entrypoint.sh L427](https://github.com/OpenHands/OpenHands/blob/v1.27.1/docker/entrypoint.sh#L427)). So an operator who sets `LOCAL_BACKEND_API_KEY` gets a UI that asks for a key and an agent server (terminal, files, conversations, settings including secret values) that does not require one. The issue was filed publicly on 2026-09-28 and is labeled bug, priority:low, ready-for-dev. #17007, merged the next day and shipped in v1.25.0, added [README.windows.md L32](https://github.com/OpenHands/OpenHands/blob/v1.27.1/README.windows.md#L32), which tells Docker users publishing on a LAN to "set `LOCAL_BACKEND_API_KEY` to a strong value", and README.md L144 offers it as one of two options. Not affected: the npm launcher, which maps the variable itself ([dev-with-automation.mjs L966](https://github.com/OpenHands/OpenHands/blob/v1.27.1/scripts/dev-with-automation.mjs#L966)), and the Helm chart, which sets `OH_SESSION_API_KEYS_0` directly ([statefulset.yaml L77](https://github.com/OpenHands/OpenHands/blob/v1.27.1/helm/agent-canvas/templates/statefulset.yaml#L77)).

**Operator consequence.** On the Docker image through v1.27.1, never set `LOCAL_BACKEND_API_KEY` alone. Set `OH_SESSION_API_KEYS_0` to the same value, or set neither and use the generated key from `$STATE_DIR/api-key.txt`. Before exposing the port, confirm from another machine that a protected `GET /api/conversations/search` request without the `X-Session-API-Key` header gets HTTP 401; server-information and initialization routes have different authentication rules. If you have run the image this way on a reachable port, treat the mounted projects and every saved secret as exposed. Watch #17763 and the next tag's entrypoint.sh; the fix is to export the key outside the `if` block. The setting the README tells you to use is the one that removes the lock, so the human check is the 401, not the prompt in the UI.

**What changed.** v1.27.0's static server imports the new DigitalOcean web bridge, but the Dockerfile copies server scripts one file at a time and never got lines for it, its eight local imports, or the `ws` package. ## 4. Profile secret scopes do not bind the agent's own terminal: the stack's session key is in its environment

- **Date:** 2026-10-06
- **Channel:** `tagged-release`
- **Ancestry evidence:** `buildAgentServerAutomationEnv` dates from 90ad71dbd9 (2026-05-19) and is present at v1.20.0 and [v1.27.1 L906-L915](https://github.com/OpenHands/OpenHands/blob/v1.27.1/scripts/dev-with-automation.mjs#L906-L915), merged into the agent-server process env at L961 (spawned with `{...process.env, ...env}`). The Docker entrypoint exports the same key under four names ([L221-L232](https://github.com/OpenHands/OpenHands/blob/v1.27.1/docker/entrypoint.sh#L221-L232)) before it starts the agent server at L306. At SDK v1.54.0 (pinned by v1.27.0 and v1.27.1), `sanitized_env` strips only `SESSION_API_KEY`, `OH_SECRET_KEY` and `OH_SESSION_API_KEYS_*` ([command.py L16-L30](https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-sdk/openhands/sdk/utils/command.py#L16-L30)), and terminals inherit everything else ([env.py L32-L38](https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-tools/openhands/tools/terminal/env.py#L32-L38)). #17279 (ea2e6dfd69) first in v1.25.0, not in v1.24.0.
- **Receipt:** https://github.com/OpenHands/OpenHands/blob/v1.27.1/scripts/dev-with-automation.mjs#L906-L915, https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-sdk/openhands/sdk/utils/command.py#L16-L30, https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/settings_router.py#L492-L522, https://github.com/OpenHands/OpenHands/blob/v1.27.1/src/api/agent-server-adapter.ts#L274-L359, https://github.com/OpenHands/OpenHands/pull/17279, https://github.com/OpenHands/OpenHands/issues/16492
- **Half:** defect | **Confidence:** high on the code path; medium on the effect (read across two repos at pinned tags, not probed live)

**What changed.** Profiles limit which saved secrets the agent server hands a conversation (section 6). But the npm and desktop launcher, and the Docker entrypoint, also export the stack's single session API key into the agent server's own environment as `OPENHANDS_AUTOMATION_API_KEY`, on purpose, so agents can call the automation service. The SDK strips the session key from terminal subprocesses only under its own names, and its source says that key must stay inside the SDK process because it unlocks user secrets. The alias passes through, so a terminal-enabled conversation on the default local runtime inherits a key the agent server accepts on every route, including the one that lists saved secrets and the one that returns any secret's raw value. v1.25.0 (#17279) also puts the runtime-services block, which names the agent-server URL and the `X-Session-API-Key: $OPENHANDS_AUTOMATION_API_KEY` header, into named-profile launches. A second path stays open: [#16492](https://github.com/OpenHands/OpenHands/issues/16492) (labeled security-related, priority:high, open since 2026-08-10) says the browser keeps every backend's key in origin-readable localStorage, and [SELF_HOSTING.md L95-L104](https://github.com/OpenHands/OpenHands/blob/v1.27.1/docs/SELF_HOSTING.md#L95-L104) warns that the bundled VS Code editor shares that origin. v1.26.0 merged a removal of the bundled editor ([#17660](https://github.com/OpenHands/OpenHands/pull/17660)) and reverted it 12 hours later for enterprise compatibility ([#18048](https://github.com/OpenHands/OpenHands/pull/18048)). The per-conversation Docker runtime passes only named variables into a container ([registry.py L411-L446](https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/docker_runtime/registry.py#L411-L446)) and filters secrets by the launched profile ([routers.py L349-L362](https://github.com/OpenHands/software-agent-sdk/blob/v1.54.0/openhands-agent-server/openhands/agent_server/docker_runtime/routers.py#L349-L362)), so that construction does not copy the outer alias wholesale. This verifies the specific difference, not universal container isolation.

**Operator consequence.** On terminal-enabled conversations using the default local runtime in npm, desktop and Docker-image installs, treat a profile's secret allow-list as a default, not a boundary: an agent that reads its environment, or one steered by injected instructions, can fetch secrets its profile excludes. Keep production and deploy credentials out of Canvas's secret store on any host where agents touch untrusted repositories. Where the scope has to hold, run conversations with `OH_CONVERSATION_RUNTIME=docker` and give the profile a secret allow-list that leaves out `OPENHANDS_AUTOMATION_API_KEY`; the cost is that the agent can no longer create automations. ## Operator questions settled

- *What happens when an agent harness becomes a full software-development platform?* Each new surface added a credential path, and this window's defects sit in the seams between the pieces: the launcher, the static server and the Docker entrypoint around the agent server's single session key (sections 1, 2 and 4), a client feature built for a server design that never shipped (section 5), and an image whose hand-kept copy list drifted from the code (section 3). The single stack-wide key is what makes every seam matter.
- *Which surfaces are SDK, CLI, GUI, cloud, enterprise, or integration-specific?* Canvas UI and launcher: OpenHands/OpenHands (npm, desktop, GHCR image, Helm chart). Agent server and SDK: OpenHands/software-agent-sdk (PyPI and GHCR). Automation service: OpenHands/automation (PyPI). Cloud and enterprise backend: OpenHands/enterprise, source-available, not open source. Hosted sandboxes: DigitalOcean Managed Agents from v1.27.0. The standalone CLI has not released since 2026-05-08.
- *How does OpenHands package sandboxing, permissions, collaboration, and evaluation for real teams?* Sandboxing: opt-in per-conversation containers with hardened run flags (section 5). Permissions: named agent profiles with server-catalog tools, persona, MCP and secret scopes, with the gaps in sections 4 and 6. Collaboration: creator-run automations and released enterprise org-member transcript readership, with hosted rollout unknown (section 10). Evaluation: an agent-driven QA harness and recipes for 27 feature families and documented known bugs shipped in the repo (section 13).
- *Which parts should teams wrap, learn from, or refuse wholesale?* Learn from the per-conversation container flags, the server-owned tool catalog that replaced three switches, and the executable feature map. Refuse: profile secret scopes as a boundary on the default runtime, `LOCAL_BACKEND_API_KEY` alone on the Docker image, the floating `latest` image and `latest-python` conversation image, and advisory feeds as a security signal.
- *Does this make agentic software work easier to adopt without hiding evidence or authority?* Mixed. Evidence improved (the feature map, more honest Docker docs after 2026-10-04), but authority is still hidden in three places: a terminal-enabled local agent inherits the stack key, conditional home-model fallback can change which profile applies, and application security fixes ship without first-party advisories while the docs site's release notes omit them.
