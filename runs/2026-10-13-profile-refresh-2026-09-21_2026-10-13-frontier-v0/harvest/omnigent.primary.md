## 3. Shell policies now ask on, or block, any command they cannot parse; git global options bypassed the GitHub policy until v0.18.0

- **Date:** 2026-10-13 (v0.18.0); earlier hardening 2026-09-22 (v0.15.0) and 2026-09-29 (v0.16.0)
- **Channel:** `tagged-release`
- **Ancestry evidence:** #9844 (d2e077a1) in v0.18.0, not v0.17.0. At v0.17.0 (github.py blob 8164293f, same at v0.16.0) `_classify_git` sets `sub = tokens[1]` and returns None for anything outside clone, fetch, pull, ls-remote and push. At v0.18.0 (blob 4fee0ed1) `_git_subcommand_index` skips known global options and yields an "unparseable" op for unknown or incomplete ones; `_classify_shell_command` turns `UnsupportedShellSyntax` into an "unparseable" op for any command; `_gate_shell_op` maps that to ASK; `block_working_dir_changes` returns its configured action, default deny. The v0.18.0 test `test_unsupported_shell_syntax_asks_even_for_benign_commands` asserts ASK for `echo $(echo ready)`, a heredoc, a comment and `$'text'`. Earlier in the window: #7999 (e6b1c83a, v0.15.0) routes `find -exec`, `xargs`, `python -c` and stdin-fed shells to the fail-safe; #7872 (2ead29d3, v0.16.0) fails closed at the nesting limit; #7871 (47f9ae32, v0.16.0). Code default for `shell_tools` is every harness's shell tool (`_shell.py` SHELL_TOOLS); POLICIES.md still lists `["sys_os_shell"]`.
- **Receipt:** https://github.com/omnigent-ai/omnigent/blob/v0.17.0/omnigent/policies/builtins/github.py#L729-L742, https://github.com/omnigent-ai/omnigent/blob/v0.18.0/omnigent/policies/builtins/github.py#L556-L613, https://github.com/omnigent-ai/omnigent/blob/v0.18.0/omnigent/policies/builtins/github.py#L943-L986, https://github.com/omnigent-ai/omnigent/blob/v0.18.0/omnigent/policies/builtins/working_dir.py#L363-L369, https://github.com/omnigent-ai/omnigent/blob/v0.18.0/docs/POLICIES.md#L347-L367, https://github.com/omnigent-ai/omnigent/blob/v0.18.0/tests/policies/builtins/test_github.py#L557-L573, https://github.com/omnigent-ai/omnigent/blob/v0.18.0/omnigent/policies/builtins/_shell.py#L29-L39
- **Half:** both | **Confidence:** high

**What changed.** The parser that `github_policy` and `block_working_dir_changes` use to read shell strings has needed fail-open fixes in June (advisory GHSA-7mqg), in September (#7999 and #7872) and now in October (git global options). v0.18.0 stops trying to model everything. Comments, heredocs and here-strings, line continuations, `$(...)` and backtick substitutions, and `$'...'` or `$"..."` quoting are declared unclassifiable. Under `github_policy` such a command adds an ASK even when it has nothing to do with git; under `block_working_dir_changes` it gets the configured action, deny by default, which the docs say "also applies when the visible command does not change directories"; a DENY from a classified region retains precedence. Both policies inspect every harness's shell tool by default (Bash for Claude Code and Codex, bash, Shell, terminal, developer__shell, shell and sys_os_shell), although POLICIES.md still documents the default as `sys_os_shell` alone. The bypass itself granted no new GitHub rights; it let an agent use the credentials it already held past the repo, branch, force-push and tag-push rules.

**Operator consequence.** If you attach `github_policy`, expect approval prompts on ordinary commands that use a heredoc or `$(...)`, a common way agents write multi-line commit messages; if you attach `block_working_dir_changes` with its default deny, those commands now fail outright, and unattended runs will stall or error. Set `action: ask` or narrow `shell_tools`, then measure the ASK volume after upgrading, because this release moves cost from the parser to whoever answers approvals. Treat shell-string policies as a filter, not a boundary: the advisory's own workaround is least-privilege credentials, and independent filesystem and credential restrictions remain necessary. The bubblewrap advisory in section 13 means an unspecified or old sandbox cannot be assumed to provide complete containment.

**What changed.** Three routes that let a shared-session editor act outside the agent closed. Approval did not move: answering pending prompts, which the docs define as policy approval gates, harness permission prompts, questions and plan review, still needs only Edit, and v0.15.0 made that a named constant whose comment says raising it to owner needs a "waiting for the owner" UI first. The website now says it plainly: "Only share Edit with people you trust to run arbitrary code on your machine."

**Operator consequence.** On v0.15.0 or later an Edit share is no longer a direct host shell, but it is still code execution through the agent plus the power to approve that agent's gated actions. Keep `public_sharing_max_level` at read: raised, any session whose owner sets General access to Edit lets every signed-in user with the link answer that session's approvals and put a Codex session into Full Access on the owner's machine.
