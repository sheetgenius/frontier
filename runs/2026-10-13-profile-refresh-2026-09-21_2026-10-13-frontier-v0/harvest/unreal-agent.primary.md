**What changed.** The project now ships a terminal client: "A minimal terminal client for Harness. Run it from your workspace" (README L3). The Homebrew cask installs it as `unreal-agent`, `uat` and `unreal-agent-tui`. Its workspace is whatever directory you launch it from (`os.Getwd()`, run.go L190). Human attention moves from per-command review, which this tool never asks for, to one decision per session: which box it runs in. That matches the vendor's stated view that approvals belong in "deterministic environment or sandbox constraints, outside the harness" (launch post, item 9), but the TUI ships no such box.

## 3. The runner trusts its workspace: a repository's .env can choose the endpoint that receives your API key, and the maintainers call that the design

- **Date:** 2026-09-23
- **Channel:** `tagged-release`
- **Ancestry evidence:** The behavior is unchanged at every tag. `loadDotEnv(filepath.Join(workspace, ".env"))` is at run.go L227 at v0.1.1 and L222 at v0.3.1. At v0.3.1 it runs before the provider is read (L235), before the base URL is read (L243) and before the key is resolved (L258), all through `getenv`, which is `os.Getenv` (cmd/internal/agentrunner/main.go L13). Issue #5 was filed 2026-09-23T02:10:03Z and is open on 2026-10-13. The maintainer reply is dated 2026-09-23T14:53:45Z; it comes from g-logunov, who commits as gleb@unreallabs.ai and tagged v0.2.0. A `git grep` over every *.md file at v0.3.1 finds no mention of `.env`, `SANDBOX_EGRESS_PROXY` or a trusted-workspace requirement.
- **Receipt:** https://github.com/unreallabsai/unreal-agent/blob/v0.3.1/cmd/internal/agentrunner/run.go#L222-L258, https://github.com/unreallabsai/unreal-agent/blob/v0.3.1/cmd/internal/agentrunner/run.go#L525-L565, https://github.com/unreallabsai/unreal-agent/blob/v0.3.1/harness/llm/clients/openai/client.go#L28-L46, https://github.com/unreallabsai/unreal-agent/issues/5#issuecomment-5797105219
- **Half:** defect | **Confidence:** high

**What changed.** The code did not change; the record did. A reporter showed on 2026-09-23 that the runner loads `<workspace>/.env` and then uses its `UNREAL_HARNESS_LLM_BASE_URL` with the operator's existing key, needing "no prompt injection or tool execution" (#5). The maintainer replied that `cmd/unreal-agent-runner` and `cmd/internal/agentrunner` "are intended for unsupervised agents in a trusted environment: workspace, host, proxies etc." The code at v0.3.1 matches that account. Every `NAME=value` in `.env` whose name is not already set in the process is applied (L550-L558). A `SANDBOX_EGRESS_PROXY` from the file wins even over an operator-set value, and it is copied into `HTTPS_PROXY` (L552, L559-L561). The provider, base URL and key are then read from the environment. The openai client sends `Authorization: Bearer <key>` to `<base URL>/responses` without checking the destination (openai/client.go L32-L41); the openrouter, fireworks, ollama and anthropic clients take a base URL the same way, and only `openai-codex` pins its host. Bash children inherit the process environment, so values from `.env` also reach every command the agent runs. The Docker image mounts the project at /workspace and loads that project's `.env` too. The TUI does not load `.env`. Since v0.3.1, the Homebrew cask puts this runner on PATH on developer machines.

**Operator consequence.** Use the runner the way the maintainers describe it: only on a workspace you already trust. Do not use `unreal-agent-runner` to vet an unknown repository, even for a read-only review. Inspect or delete its `.env` first, or use the TUI, which ignores `.env`, inside a sandbox. If you must run it on untrusted code, export `UNREAL_HARNESS_LLM_PROVIDER` and `UNREAL_HARNESS_LLM_BASE_URL` yourself, because values you set win over the file's. Do not treat `SANDBOX_EGRESS_PROXY` as an enforcement point, since a workspace file can replace it; enforce egress at the network layer. The maintainers frame this as the intended trust boundary. #5 is still open, and no fix commit exists. The trust decision lands on the operator's choice of directory, and the tool never surfaces it.

**What changed.** At v0.1.1 the runner kept sessions in `.harness/sessions`, relative to the process's current directory, and by default wrote a JSONL log to `<workspace>/logs`. Issue #3 (2026-09-22) showed the cost: a background `grep -R .` read its own capture file inside the workspace, the file reached 61.8 GB in about ten minutes, and the runner never exited. The maintainer answered on 2026-09-23 that the log default "wasn't the intended behaviour" and promised fixes for both problems. v0.2.0 shipped them the same evening. Sessions now live under `$XDG_STATE_HOME/unreal-agent/sessions` (default `~/.local/state/unreal-agent/sessions`), the log is written only with `-log-directory`, and the Docker image gained a writable `/state` directory and `XDG_STATE_HOME=/state`; the README shows mounting a named volume there. The release body names the XDG-state and opt-in-log change; it does not explain the old-session lookup trap. The upgrade trap sits in `openSession`, which at every tag creates a fresh session when the requested `session_id` is not found.
