**What changed.** A plugin can now carry a mod: JavaScript or TypeScript handlers that run inside the Claude Code process on its events, including `tool.call` (rewrite any tool call), `prompt.submit` and `tool.check` (the permission verdict). Mods run unsandboxed as the user. Several of Claude Code's own features now ship as built-in mods, and the source of four (AGENTS.md loading, `/diff`, telemetry and an organization guard) is public. The permission model moved with it: a mod's `tool.check` answer comes after deny and ask rules and settings hooks and can replace them, so an installed mod can approve a call an ask rule would prompt for or a non-managed PreToolUse hook blocked, and in auto mode its approval skips the classifier. Deny rules hold over a user's mod only where the guard loads (managed settings present, or a Team or Enterprise sign-in); on a Pro or Max laptop, or an API-key, Bedrock, Vertex or Foundry machine without managed settings, a mod can approve a call a deny rule refuses. Mods went from flag-off early access to on by default in 2.1.286, and 2.1.287 stopped honoring the early-access off switch, and one approval lets every mod Claude writes in that session load and reload.

**Operator consequence.** Managed fleets: set `pluginConfigs["cc-plugin-sec-default@builtin"].options.allowManagedModsOnly: true` (read only from managed settings, fails closed) and `disableSideloadFlags` (stops `--plugin-dir`, `--plugin-url` and Claude-written mods, and also rejects `--agents` and `--mcp-config`). Check CI invocations before applying that lock. A fleet that set `CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=0` has had mods on since it reached 2.1.287. Stable 2.1.287 lacks the guard fixes from 2.1.289 through 2.1.295, so on stable the option is the control and the guard's deny holding is not; managed fleets that allow mods should set managed `requiredMinimumVersion` to 2.1.295 or later. Unmanaged machines: a deny rule no longer stops an installed mod, so review plugins with `claude plugin validate` (the `hooks:` line names `tool.check`), or use `--safe-mode`/`disableAllHooks`, which do not stop built-in mods. A Read deny never covered a mod's own `$.fs.read`. The review burden moved: approving a plugin now means reading code that runs in-process with permission authority.

**What changed.** On every released build the guard holds only deny rules over a user's mod: even where it loads, an installed mod can turn an ask from a rule or a non-managed hook into an allow, and nothing stops its `$.env.set`, which reaches every command and MCP server the session starts afterward. **What changed.** Before 2.1.283 auto mode was the built-in starting mode only on Pro, Max and Team. Now an interactive terminal or VS Code session with no configured mode starts in auto on every plan and provider, Enterprise, API keys, Bedrock, Vertex, Foundry and gateways included, and from 2.1.285 so does a `claude -p` or Python Agent SDK run on a third-party provider or with telemetry off. Anthropic's own repository does not run it that way: its CLAUDE.md requires an egress-firewall runner, an enforced allow list and auto mode together for every job that calls Claude. Two classifier behaviors moved on latest only: a custom subagent with `permissionMode: auto` ran in auto mode even where `disableAutoMode` removed it (fixed 2.1.292), and the instruction that a denial covers the outcome, not just the command, was withdrawn (2.1.293).

**Operator consequence.** A Bedrock, Vertex or Foundry CI job that runs `claude -p` without `--permission-mode` changed authority model when stable reached 2.1.285 on 2026-09-30: what used to go to the SDK host, the prompt tool or a `--permission-prompts none` denial is now a classifier decision. For untrusted-input jobs copy the vendor's own pattern: auto mode plus an enforced egress allow list, not auto mode alone. The human gate moved from answering prompts to deciding, per job, whether a model may answer them.
