- **Half:** both | **Confidence:** high (code reading; no evaluation was run against TypeSafe)

**What changed.** Gated calls park as workflow waits until a model or human decision resolves them. Auto mode adds argument-aware decisions against named criteria sets. In the generic harness, a tool without criteria goes to a person without a model call; evaluator errors or unusable results escalate; a human answer cancels pending evaluation; evaluations are bracketed on the event stream. With the built-in Jev evaluator, confidence below min_confidence (default 0.8) escalates, and an approve judged too irreversible (default ceiling 0.5) escalates. These numeric thresholds are Jev behavior, not independent enforcement on every custom evaluator. A confident DENY resolves the call without asking a person, contrary to the release note that every non-approval reaches one. Jev sends the tool name, description, exact arguments, criteria and optional extra_state to TypeSafe System One from the worker; the request is also an activity input in workflow history. Its default model is jev-latest; the pinned integration README recommends a fixed version because calibration can change. remember=True adds a bare tool name above auto mode, which is bypassed while the tool remains on the by-name allow-list. Subsequent policy replacement or name removal can restore gating. Each evaluation records its criteria set name/version; live criteria are not shown on AgentStatus.

**Operator consequence.** Try this for repetitive low-risk decisions with criteria that escalate or deny consequential calls. Enable the policy and wire an evaluator; Jev needs the jev extra and TYPESAFE_API_KEY on the worker. Pin agent.jev_evaluator(model=...) to a concrete version and treat TypeSafe as a processor of gated call arguments. Audit auto_approval_evaluation_ended events for unattended denials. Avoid Always allow on a tool whose arguments should keep being evaluated. No live evaluation or TypeSafe retention behavior was checked.

## Operator questions settled

- **Q1, does OpenCode's "always" map to `remember` and approve later bash commands regardless of arguments:** yes, while the name remains allowed, at 0.6.0 (prior claims above). - **Q4, what a tool must be for "no double-run" to hold:** unchanged at 0.6.0; activity tools need their own idempotency strategy for retryable side effects; there is no harness exactly-once guarantee.
