**What changed.** 1.0.93 makes "Command sandboxing ... available to all users via /sandbox and --sandbox" (L42); until then the CLI docs called it experimental. GA did not turn it on. - **Date:** 2026-09-28 to 2026-10-07
- **Channel:** `docs-only` (enforcement descriptions in `03b432e6d532`); `tagged-release` for 1.0.89 L154 and 1.0.93 L36
- **Ancestry evidence:** Before-state, pinned at github/docs `2c5e31e02c95` (parent of `03b432e`): macOS "does not give the proxy to Seatbelt", and a program that ignores the proxy variables connects directly (about-cloud-and-local-sandboxes.md L112); host rules run through a proxy "that enforces them strictly on every platform" (cli-config-dir-reference.md L543, introduced 2026-09-15 in `3b332a9`); `allowLocalNetwork` defaults to `true` (L502). After, at `602021b0ba16`: about page L107-L108, cli-config-dir-reference.md L503 and L546, configuring-local-sandbox-settings.md L250, L258-L266 and L291. No changelog line names a macOS enforcement change. MXC source corroborates the mechanism, and MXC already had the same Seatbelt proxy rule at v0.8.0 (2026-08-22).
- **Receipt:** https://github.com/github/docs/blob/2c5e31e02c95/content/copilot/concepts/security-governance-and-network-settings/about-cloud-and-local-sandboxes.md?plain=1#L112 , https://github.com/github/docs/blob/602021b0ba16/content/copilot/how-tos/cloud-and-local-sandboxes/configuring-local-sandbox-settings.md?plain=1#L250-L291 , https://github.com/microsoft/mxc/blob/v1.0.0/src/mxc-sdk/src/backends/seatbelt/common/profile_builder.rs#L507-L536 , https://github.com/microsoft/mxc/blob/v1.0.0/docs/backends/seatbelt/seatbelt-backend.md?plain=1#L274-L315
- **Half:** both | **Confidence:** medium (vendor docs plus engine source; Copilot's own wiring of MXC not probed)

**What changed.** Three statements flipped on 2026-10-07. (a) Egress: on macOS and Linux "the sandbox restricts outbound connections to the local proxy", so programs that ignore proxy settings cannot connect directly. On Windows "the sandbox relies on programs honoring the proxy settings", and programs that ignore them "can connect directly and get around your host rules" (about page L107-L108; config ref L546; how-to L291). From 2026-09-15 until that commit, the docs had said host rules were enforced strictly on every platform. (b) Local network: `Allow local network` is "Turned off by default" in the CLI (how-to L250; config ref L503), unlike the app. (c) macOS self-connect: when a local proxy is active on macOS, turning local access on "lets a command listen on a port, but does not let it connect directly to that port itself", and credential masking for Git and `gh`, which is on by default, always starts that proxy (how-to L264-L266). Two binary changes in window loosened the 1.0.83 localhost cut: on Windows, sandboxed commands can reach localhost when local access is on (1.0.89, L154), and local-network allowlists now include localhost and loopback (1.0.93, L36; config ref L505). The engine explains (c). With a proxy set and outbound denied by default, MXC's Seatbelt builder emits only `(allow network-outbound (remote ip "localhost:<proxy-port>"))` (profile_builder.rs L507-L520), and allowing local network adds only `(allow network-inbound (local ip))` (L530-L536). MXC's own doc warns that opening host loopback would widen outbound to every local port, and that a listener bound to 0.0.0.0 can be reached from the LAN (seatbelt-backend.md L298-L308).

**Operator consequence.** Re-test anything sandboxed that talks to localhost. On macOS with default credential settings, a test suite that starts a server and then connects to it can fail even with Allow local network on. The only case the docs describe where a command can connect to a local server is "no proxy, host rules, or credential masking" (L258), which means turning off Git and `gh` credential injection for that work. Bind listeners to 127.0.0.1, because 0.0.0.0 exposes them to the network. On Windows, treat `allowedHosts` and `blockedHosts` as advisory and keep an OS firewall rule if egress matters. Check `/sandbox policy` on your own hosts before trusting either page; this lane did not run the binary.

## 4. Sandboxed commands now get placeholder credentials: GITHUB_TOKEN withheld (1.0.92), and a local proxy injects the real Git, gh and chosen secrets per host

- **Date:** 2026-10-01 to 2026-10-12
- **Channel:** `tagged-release` (1.0.91 L93; 1.0.92 L60, L75; 1.0.95 L16; 1.0.96 L3); `docs-only` for the masked-variable how-to (`64d77f5e0fcf`, 2026-10-08)
- **Ancestry evidence:** All four are prerelease=false releases: v1.0.91 at 2026-10-01T17:25:02Z, v1.0.92 at 2026-10-05T19:42:08Z, v1.0.95 at 2026-10-09T16:04:26Z and v1.0.96 at 2026-10-12T18:52:01Z. The docs commit is `64d77f5e0fcf`, "Document masked secrets for Copilot CLI local sandboxing". The token exposure dates to 0.0.404 ("GITHUB_TOKEN environment variable now accessible in agent shell sessions", L2701).
- **Receipt:** https://github.com/github/copilot-cli/blob/a3f560eca2c0/changelog.md?plain=1#L60 , https://github.com/github/copilot-cli/blob/a3f560eca2c0/changelog.md?plain=1#L75 , https://github.com/github/copilot-cli/blob/a3f560eca2c0/changelog.md?plain=1#L93 , https://github.com/github/docs/blob/602021b0ba16/content/copilot/how-tos/cloud-and-local-sandboxes/configuring-local-sandbox-settings.md?plain=1#L155-L157 , https://github.com/github/docs/blob/602021b0ba16/content/copilot/how-tos/cloud-and-local-sandboxes/using-local-sandboxing.md?plain=1#L103 , https://github.com/github/docs/blob/602021b0ba16/content/copilot/how-tos/cloud-and-local-sandboxes/using-local-sandboxing.md?plain=1#L176-L182
- **Half:** capability | **Confidence:** high on the text; not probed

**What changed.** In 1.0.92, sandboxed shells "withhold ambient GITHUB_TOKEN unless explicitly configured" (L60), and sandboxed Git authenticates "with masked credentials and SSH remote rewrites" (L75). 1.0.91 adds `copilot sandbox ca` to create, trust, rotate and remove the proxy's CA (L93). Per the docs, sandboxed processes get placeholders. The local proxy supplies real Git credentials only at their original host, port and repository path, and the real `gh` token only to github.com, api.github.com and uploads.github.com (how-to L155-L156). For any other secret, `sandbox.credentials.envVars.<NAME>.injectHosts` masks the variable, and the proxy puts the real value only into HTTPS request headers sent to the listed hosts (config ref L502; how-to L157). 1.0.95 lets `copilot config` set injectHosts keys (L16), and 1.0.96 suggests likely secrets in the settings dialog (L3). The docs state four limits. A full approved bypass "skips credential masking and the sandbox proxy", restoring the ordinary environment, which can contain real secrets (using L103). Masking does not hide credential files, other variables, or remote MCP auth (L182). Trusting the CA in the OS store "also changes certificate trust for applications outside" the CLI (L176). On Windows, masking needs Allow local network, which also opens private-network access.

**Operator consequence.** The vendor documents withholding ambient GITHUB_TOKEN unless configured, and placeholder substitution for configured masked variables and enabled Git/gh authentication. Exfiltration resistance has not been tested; credential files and unmasked variables remain outside this protection. List the API tokens your agent uses as masked variables with tight injectHosts. Install the CA in the OS trust store only if a tool requires it, because that changes trust outside the CLI. Token files such as ~/.npmrc remain a separate exposure under default developer-tool access. A full bypass restores the ordinary environment, which can contain real secrets. The proposed attention saving is less inspection of ambient credentials in every command; the new maintenance cost is an injection-host list per secret.

## 5. 1.0.93 adds `permissions.limitTo`, a managed domain boundary that allow-all cannot widen

- **Date:** 2026-10-07
- **Channel:** `tagged-release`
- **Ancestry evidence:** v1.0.93 as in item 2 (prerelease=false, 2026-10-07T14:06:47Z). Docs arrived in github/docs `2b461a06671e` (2026-10-07T09:24:52Z), a sync from the CLI's source docs.
- **Receipt:** https://github.com/github/copilot-cli/blob/a3f560eca2c0/changelog.md?plain=1#L33 , https://github.com/github/docs/blob/602021b0ba16/content/copilot/reference/copilot-cli-reference/cli-config-dir-reference.md?plain=1#L708-L726
- **Half:** capability | **Confidence:** high on the text; not probed

**What changed.** "Add enterprise permissions.limitTo to enforce managed domain boundaries for network requests" (L33). The docs define it this way. It takes `Domain(...)` entries only, and a request to a domain outside the list "is denied without prompting, and user rules, saved approvals, and allow-all modes can't widen it". "URLs detected in shell requests" count as Domain requests. An empty list denies every domain, and an invalid list is enforced as empty instead of discarding the rest of the policy. `deny` still wins over `limitTo`, while `ask` and `allow` only refine requests already inside the boundary. Every managed source that sets `limitTo` must admit a request (intersection). It "doesn't restrict `shell`, `read`, or `write` operations by themselves" (L722-L726).
