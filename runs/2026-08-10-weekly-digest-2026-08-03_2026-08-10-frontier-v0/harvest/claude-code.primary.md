## 1. Shell-command permission checks could be shown one command and run another -- fixed across v2.1.221 to v2.1.223

- **Date:** 2026-08-06 | **Version:** v2.1.221, v2.1.222, v2.1.223
- **Channel:** `tagged-release` (in a stable tag an operator can install)
- **Ancestry evidence:** Closed source; npm publish record is the release proof. registry `time[]`: 2.1.221 = 2026-08-03T22:16:25Z, 2.1.222 = 2026-08-04T20:37:17Z, 2.1.223 = 2026-08-05T22:51:13Z -- all plain non-prerelease semver under dist-tag `latest`, all reachable as per-version manifests. Note the date skew between surfaces: the changelog dates 2.1.221 and 2.1.222 to August 4 and 2.1.223 to August 6, while the registry timestamps are August 3, 4 and 5 UTC. I take the registry timestamp as the authority for window assignment since it is the artifact's own publish time; all three fall in w1 either way.
- **Receipt:** https://code.claude.com/docs/en/changelog#2-1-223
- **Half:** defect | security-relevant | **Confidence:** high

**What changed.** Three consecutive releases fixed the same class of defect: the string the approval dialog showed the human was not the string that ran. v2.1.221 -- "a Bash tool permission-check bypass where zsh could execute hidden commands in `[[ ]]` regex conditionals", plus PowerShell checks mishandling paths containing quote characters on Windows. v2.1.223 -- "a Bash permission bypass where a crafted command could hide parts of itself from permission checks", and "permission prompts so commands padded with tabs or invisible Unicode can no longer hide part of the command from the approval dialog." v2.1.223 also closed three authority gaps: "workflow scripts being able to use dynamic `import()` to run code outside the workflow sandbox", and "a permission gap where an agent definition's `bypassPermissions` mode ignored the org bypass-permissions disable policy" -- an agent definition overriding organizational policy. v2.1.222 closed two more: worktree-isolated sessions and their subagents "being able to run destructive git commands against the main checkout", and "PreToolUse auto-allow hooks bypassing tool restrictions in background agent tasks (summaries, compaction, renames)." v2.1.224 added one more of the same shape: sandbox filesystem deny entries "written with a trailing slash (e.g. `denyRead: "~/.aws/"`) being silently bypassable on Linux and macOS."

**Operator consequence.** Upgrade past 2.1.224, then go and read your own sandbox deny rules. The trailing-slash defect is the one that silently invalidated configuration operators had written and believed in -- anyone who spelled `denyRead: "~/.aws/"` had no protection on that path at all, and nothing reported it. Separately, the invisible-Unicode and command-hiding fixes mean approval logs from before this window are not reliable evidence of what ran: if you retain transcripts for audit, the recorded approval and the executed command may differ. The `bypassPermissions`-ignoring-org-policy gap deserves its own check -- enumerate your custom agent definitions and confirm none of them was relying on a mode your organization thought it had disabled.

## 2. Claude Code sessions can now message each other, and `@` mentions another session by name

- **Date:** 2026-08-07 | **Version:** v2.1.224 (cross-session messaging), extended in v2.1.232 (`@` mention, bare-name delivery, unique names)
- **Channel:** `tagged-release` (in a stable tag an operator can install)
- **Ancestry evidence:** Closed source; npm publish record is the release proof. registry `time[]` gives 2.1.224 = 2026-08-07T01:36:32Z and 2.1.232 = 2026-08-13T21:30:53Z, both plain semver under dist-tag `latest`. The feature is documented on its own docs page, https://code.claude.com/docs/en/cross-session-messaging (HTTP 200), and the Week 32 digest pins it to v2.1.224 with the line "Requires v2.1.224 or later" -- a version pin, so this is a code channel and not a marketing surface.
- **Receipt:** https://code.claude.com/docs/en/whats-new/2026-w32
- **Half:** capability | security-relevant | **Confidence:** high

**What changed.** v2.1.224 added cross-session `SendMessage`: "Claude Code sessions can now message each other, on any of your machines, with `ListAgents` to discover them (macOS and Linux)." The digest is precise about the payload boundary -- "A message is text Claude writes for the other session, never your conversation history or files." v2.1.232 made it usable: typing `@` in the prompt mentions another session by name, `SendMessage` delivers to a bare name that exactly matches one live session instead of demanding a ref, and sessions on one machine are forced to unique names (a collision gets a `name-word-word` variant). The governance surface arrived with the feature rather than after it: v2.1.224 added `crossSessionInbound` and `dialogExpiry` settings, where "cross-session messages sent to a session running with bypassed permissions are held for your approval", and v2.1.222 put the classifier in front of the send -- "messages sent to other agent sessions via `SendMessage` are now evaluated by the permission classifier before dispatch." v2.1.232 exposed both as `/config` rows.

**Operator consequence.** Try it if you run several long-lived sessions on one machine, but decide the inbound policy deliberately rather than inheriting it. The interesting property for anyone building on Claude Code is that a message is now an untrusted input channel between agents: text one session's model wrote lands in another session's context. Set `crossSessionInbound` to hold or refuse on any session you start with bypassed permissions -- the default already holds there, and that default is the tell that Anthropic considers the channel a privilege boundary. macOS and Linux only; Windows operators can ignore this entirely for now.

## 3. Self-hosted environments run Claude Code cloud sessions on infrastructure you operate -- public beta, shipped inside a stable release

- **Date:** 2026-08-07 | **Version:** v2.1.224
- **Channel:** `tagged-release` (in a stable tag an operator can install)
- **Ancestry evidence:** The code channel and the feature's maturity label disagree, and the distinction matters. The code shipped in v2.1.224, a plain non-prerelease semver published to npm at 2026-08-07T01:36:32Z under dist-tag `latest` (per-version manifest resolves HTTP 200) -- so by channel it is a tagged release, not a prerelease. The feature is nonetheless labelled "public beta on Team and Enterprise plans" on the what's-new surface. There is no rc/beta/alpha tag anywhere in the registry `time[]` map for this window; the beta is a product-maturity claim, not a release channel. Backed by a dedicated docs page at /docs/en/self-hosted-environments-quickstart (HTTP 200).
- **Receipt:** https://code.claude.com/docs/en/changelog#2-1-224
- **Half:** capability | **Confidence:** high

**What changed.** Changelog v2.1.224: "Added self-hosted environments: `claude self-hosted-runner` turns your own machines or containers into a place Claude Code web, mobile, and desktop sessions can run, on Team and Enterprise plans." The digest fills in the control flow: when someone picks your environment from claude.ai, the mobile or desktop apps, or `claude --cloud`, "that session runs inside your network, with access to your internal services", and an Owner or admin must first enable "Allow self-hosted environments" in admin settings. The runner surface was still settling through the window -- v2.1.224 through v2.1.234 carried a steady stream of runner fixes: sessions failing on every fresh runner when a `checkout` hook fails, registration succeeding then every session failing when `--base-dir` cannot be written, repository preparation hanging on a Git Credential Manager prompt, sessions ending in the gap between a background task finishing and the follow-up turn, and Windows startup now requiring an explicit `--base-dir` because there is no default checkout directory. v2.1.229 added server-supplied hook support for runner sessions, matching managed-environment behaviour.

**Operator consequence.** Watch rather than adopt, unless you have a concrete reason cloud sessions must reach internal services. The capability itself is significant -- it is the answer for teams who wanted Claude Code's web and mobile surfaces but could not send their source to Anthropic-operated compute. But read the shape of the fix list before scheduling the migration: five separate 'runner fails on every session' defects landed in the eleven days after launch, which is what a surface looks like before its edges are known. If you do pilot it, note that v2.1.229's server-supplied hooks mean the runner accepts hook definitions from the server -- establish who can set those before you point a runner at anything sensitive.

## 4. Sandbox credential masking gains extraction, JWT-aware decoding, and AWS SigV4 re-signing

- **Date:** 2026-08-07 | **Version:** v2.1.221 (`mode: "mask"`), v2.1.224 (extract, JWT, SigV4)
- **Channel:** `tagged-release` (in a stable tag an operator can install)
- **Ancestry evidence:** Closed source; npm publish record is the release proof. registry `time[]`: 2.1.221 = 2026-08-03T22:16:25Z, 2.1.224 = 2026-08-07T01:36:32Z -- both plain non-prerelease semver under dist-tag `latest`, both with resolvable per-version manifests. Corroborated on a second surface: the Week 32 digest's "Other wins" grid links the feature to /docs/en/sandboxing#mask-credential-files, so a docs surface stands behind the changelog claim rather than the changelog standing alone.
- **Receipt:** https://code.claude.com/docs/en/changelog#2-1-224
- **Half:** capability | security-relevant | **Confidence:** high

**What changed.** v2.1.221 added `mode: "mask"` for sandbox credential files on Linux and WSL: "sandboxed commands read a sentinel copy (the whole file, or just the spans captured by an `extract` regex) while the sandbox proxy substitutes the real value on egress; on macOS file masking falls back to `deny`." v2.1.224 extended it with "`extract` and `onExtractNoMatch` for structured env values, `decode: "jwt"` with `maskClaims` for JWT-aware masking, and `awsPairs`/`sigv4` for AWS SigV4 re-signing." Both carry the same two constraints, stated plainly in the changelog: the options "need `network.tlsTerminate`" and are "honored only from user, managed, or `--settings` settings" -- a project's checked-in settings cannot configure how its own credentials are masked. Related and worth pairing: v2.1.224 also fixed "sandbox violation details never appearing in Bash tool results; Claude now sees which file or network access was denied and why."

**Operator consequence.** Try this if you run agents against services whose credentials you cannot rotate cheaply -- it is the difference between the agent holding your key and the agent holding a placeholder while the proxy holds the key. Two conditions decide whether it applies to you: it requires TLS termination at the sandbox proxy, which is itself a decision your security team should make explicitly, and macOS silently degrades to `deny` rather than masking, so a config that works on your Linux CI will behave differently on a developer's Mac. Do not assume behaviour carries across the two platforms. The settings-scope restriction is the right default and worth preserving.

## 5. Plugin marketplace supply chain: SHA-256-pinned zip archives, GitLab sources, owner wildcards -- and an allowlist that could be pointed at the wrong host

- **Date:** 2026-08-07 | **Version:** v2.1.223, v2.1.224, v2.1.232, v2.1.234
- **Channel:** `tagged-release` (in a stable tag an operator can install)
- **Ancestry evidence:** Closed source; npm publish record is the release proof. registry `time[]`: 2.1.223 = 2026-08-05T22:51:13Z, 2.1.224 = 2026-08-07T01:36:32Z (both w1); 2.1.232 = 2026-08-13T21:30:53Z, 2.1.234 = 2026-08-17T18:19:13Z (both w2). All four are plain non-prerelease semver under dist-tag `latest` with resolvable per-version manifests. The archive source is corroborated on a second surface by the Week 32 digest, which links /docs/en/plugin-marketplaces#zip-archives. Dated to w1 on the first material entry; the v2.1.234 allowlist fix is w2.
- **Receipt:** https://code.claude.com/docs/en/changelog#2-1-224
- **Half:** both | security-relevant | **Confidence:** high

**What changed.** The capability half: v2.1.224 added an `archive` plugin source -- "install plugins from a zip over HTTPS without git or npm, with optional SHA-256 pinning." v2.1.223 added owner wildcard entries (`"owner/*"`) to the `strictKnownMarketplaces` and `blockedMarketplaces` managed settings, for allowing or blocking every marketplace repo under a GitHub org. v2.1.232 brought GitLab into the marketplace system (bare `gitlab.com` URLs including nested subgroups now clone like `github.com` URLs) and added `additionalMarketplaces`/`allowedMarketplaces` as friendlier aliases for the existing keys. The defect half is the one to read carefully: v2.1.234 fixed "`strictKnownMarketplaces` allowlists accepting SCP-style git marketplace sources whose host differs from the one git would actually connect to" -- the allowlist validated one host while git connected to another. v2.1.232 also fixed "a startup race that could silently unregister a plugin marketplace due to concurrent writes to `known_marketplaces.json`", and v2.1.223 fixed a url-typed `blockedMarketplaces` entry ceasing to block once the CLI reclassified the URL as a git clone.

**Operator consequence.** Upgrade to 2.1.234 if you enforce `strictKnownMarketplaces`, and treat the pre-2.1.234 allowlist as advisory rather than enforced. The SCP-style host-mismatch bug is the sharpest item here: an allowlist is a security control whose entire value is that it is exact, and this one could be shown `git@github.com:org/repo` while git dialled somewhere else. The `blockedMarketplaces` reclassification bug is the same failure in the other direction -- a block that stopped blocking. Re-verify both lists against what your machines actually cloned. On the capability side, the SHA-256 pin on `archive` sources is worth adopting: it is the only plugin install path in this window that gives you content addressing rather than trust in a host.

## 6. Ultraplan research preview removed, `/review` folded into `/code-review`, and context-window enforcement tightened on unknown models

- **Date:** 2026-08-05 | **Version:** v2.1.222 (ultraplan removal), v2.1.223 (context enforcement, /review alias)
- **Channel:** `tagged-release` (in a stable tag an operator can install)
- **Ancestry evidence:** Closed source; npm publish record is the release proof. registry `time[]`: 2.1.222 = 2026-08-04T20:37:17Z and 2.1.223 = 2026-08-05T22:51:13Z, both plain non-prerelease semver under dist-tag `latest` with resolvable per-version manifests. Corroborated on a second surface: the Week 32 digest's "Other wins" grid states "The Ultraplan research preview is removed, including the `/ultraplan` command and the `ultraplan` keyword; use plan mode or Claude Code on the web instead" and links /docs/en/ultraplan, and separately confirms the `/review` alias.
- **Receipt:** https://code.claude.com/docs/en/changelog#2-1-222
- **Half:** both | **Confidence:** high

**What changed.** v2.1.222 ends with a single line -- "Removed ultraplan feature" -- retiring a research preview that entered early preview in Week 15 (April 2026) as cloud-drafted plans reviewable in a web editor. The digest names the migration path: plan mode or Claude Code on the web. v2.1.223 rationalised review: "`/review` is now an alias of `/code-review`, which reviews the current diff or a PR (`/code-review <level> <pr#>`); use `/code-review ultra` for a deep cloud review", and `/code-review` with no level reuses the last level typed. v2.1.223 also changed two context-window behaviours with cost consequences: `CLAUDE_CODE_DISABLE_1M_CONTEXT` now "hold[s] every Claude model with a native 1M window to 200K via auto-compaction, not just a fixed list", with a startup warning when auto-compaction is not holding the session to 200K; and auto-compact now keeps sessions on unrecognised model IDs "within the assumed context window instead of letting them grow past it" (`CLAUDE_CODE_DISABLE_UNKNOWN_MODEL_WINDOW_ENFORCEMENT=1` restores the old behaviour). v2.1.234 cut the built-in `claude-api` skill's context cost "from ~200k+ tokens to ~25k by loading reference docs on demand."

**Operator consequence.** Adapt if you scripted `/ultraplan` -- it is gone with no deprecation window, and a keyword-triggered workflow will now simply not fire. The context-enforcement changes are the ones to watch on a bill: if you were relying on `CLAUDE_CODE_DISABLE_1M_CONTEXT` naming a fixed model list, it now covers every 1M-native model, which will change compaction behaviour on models you did not intend to constrain; and if you route through a gateway that presents model IDs Claude Code does not recognise, sessions that previously grew unbounded are now held to an assumed window. Both are improvements, and both change token accounting from one release to the next -- re-baseline before you read a cost regression as a model change.

## Researcher lane notes

HARVEST SHAPE. Fourteen changes from thirteen releases (v2.1.221 -- v2.1.234) plus one cross-cutting channel finding. Both halves are present and the split is roughly even: five capability entries (cross-session messaging, self-hosted environments, subagent forking by default, sandbox credential masking, auto mode as default), five defect entries (the two Windows NTLM path fixes, the v2.1.232 seven-item bypass cluster, the v2.1.221 -- 223 shell-permission cluster, the gateway policy fix), three marked `both`, and one `neither` on each end (the channel-lag finding and the todo-tools removal). The window's centre of gravity is unmistakably the pre-approval boundary: by my count roughly twenty distinct entries across these releases describe a way the permission check could be shown one thing while another thing happened. That is a lot for two weeks, and it is the story here.

ANCESTRY GAP -- the material limitation of this lane. Claude Code is closed-source. Rule 3's prescribed proofs are unavailable, not merely inconvenient. I substituted the npm registry publish record (version = tag) and said so in every single `channel_evidence` field rather than letting a plausible-looking classification imply an ancestry check I did not run. Readers should weight these channel calls accordingly: they prove publication, not containment. The compensating control is that every `what_changed` quotes Anthropic's changelog text for that specific version, so the version-to-change binding comes from the publisher, not from me.

SURFACE DISAGREEMENT WORTH RECORDING. Changelog authored dates and npm publish timestamps skew by up to about a day (2.1.221: changelog says Aug 4, registry says 2026-08-03T22:16:25Z; 2.1.225: changelog Aug 8, registry 2026-08-07T23:08:56Z). Both are late-evening UTC publishes being dated to the following day. I used the registry timestamp for window assignment since it is the artifact's own publish time. No change crosses the w1/w2 boundary under either reading, so nothing is contingent on the choice.

UNRESOLVED: v2.1.230. Absent from the npm `time[]` map entirely and absent from the changelog. It was not unpublished -- npm retains a `time[]` entry for unpublished versions -- so the number appears to have been burned or a build withheld between 2.1.229 (Aug 12) and 2.1.231 (Aug 13, a single-fix release for MCP OAuth against Slack). I could not resolve why from any primary surface and am not going to guess. Recording it because a skipped release number between two same-day releases is the shape of a pulled build, and if a later window turns up a reason this is the anchor for it.

SINGLE-SURFACE CLAIMS, flagged honestly. The gateway managed-settings policy fix (v2.1.232) rests on the changelog alone with no corroborating docs page; I marked it confidence: medium for that reason and no other -- the entry itself is unambiguous. Most Remote Control entries are likewise changelog-only, but the one with governance consequence (auto-start no longer enablable from repo-local settings) is corroborated by the Week 32 digest. Every other change is carried by two or more surfaces.

SECURITY-ADVISORY DISCIPLINE. Applied the standing rule in sources/claude-code.notes.md: Anthropic publishes no separate advisory feed for Claude Code, so the changelog is the de-facto advisory surface and advisory-shaped entries were promoted on that basis. No CVE or GHSA exists for anything in this window; I checked no third-party aggregator and cite none. Vulnerability classes named in plain language where determinable: credential disclosure via forced NTLM authentication (the `\??\` path vector, Windows-only, and notable because the v2.1.234 half covers files read BEFORE any permission prompt -- CLAUDE.md includes, session restore, workflow scripts -- so no user error was required); permission-check bypass (PowerShell `$PSDefaultParameterValues`, zsh `[[ ]]` conditionals, invisible-Unicode padding, Cygwin symlinks); sandbox escape (Linux protected-path, workflow dynamic `import()`, `/tmp` symlink planting); trust-boundary failure (nested repositories, Remote Control bridge credential inheritance); and privilege misassignment (malformed `admin_groups` granting rather than denying admin).

THE FINDING I WOULD LEAD WITH. Not any single fix, but the intersection of two facts that only appear together when you check both a package surface and a docs surface: this window shipped the densest run of permission-bypass fixes I have seen from this source, AND the documented conservative channel -- the one a cautious enterprise would choose, and which Anthropic's own Homebrew and apt instructions default to -- did not receive any of them. `stable` was pinned at 2.1.226 on 2026-08-17 while `latest` stood at 2.1.234. The team that followed the careful advice is the team running the bypassable build. That is the cleanest illustration of this publication's thesis I could have asked the surfaces for, and it took the registry dist-tags plus the setup docs to see it -- neither surface shows it alone.

NOTHING FABRICATED. Every receipt returns HTTP 200 as of 2026-08-17; I verified changelog, permission-modes, sandboxing, setup, whats-new/2026-w32, cross-session-messaging, self-hosted-environments-quickstart, and five per-version registry manifests directly. Changelog receipts use per-version anchors (`#2-1-234`), the anchor format Anthropic's own digest pages link with -- these are the most stable pin available for a source with no tags, though the reader should know the changelog is a single rendered page that grows, so the anchor is stable while the page is not immutable.
