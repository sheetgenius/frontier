## 1. Origin lets an agent's ownership decision, or an installed app's approval, satisfy code-owner review

- **Date:** week of 2026-10-12 (vendor label spanning 12 to 18 October; no capture of the notes page before 2026-10-24); read 2026-10-24
- **Channel:** `docs-only` (hosted ruleset option); supporting protocol fields first appear in Origin CLI stable artifact 2026.10.23-18-47-36-f52be1e
- **Ancestry evidence:** The 2026-10-24 capture of the Origin notes carries the week of 2026-10-12 with the new Code owner review setting (Off, Classic, Agentic) and app code owners; the parent run's 13-14 October reads cited no such note, and neither item has an API changelog date. The public Create Ruleset reference still exposes only the boolean `requireCodeOwnerReview`, so Agentic exists only in the web editor as documented. String comparison of the hash-checked bundles: `human_review_required`, `botOwners`, `ChangesetOwnerRule` and the `required_reviewer_approval` blocker are absent from stable 2026.10.13-14-06-43-ea1dfe5 and present in stable 2026.10.23-18-47-36-f52be1e; the `RecordAgenticOwnersRiskRating` message (tier, model, policy commit, recommended reviewers) is present in both, so the rating machinery predates the window. No runtime test.
- **Receipt:** https://web.archive.org/web/20261024092622/https://cursor.com/docs/release-notes/origin#oct-12-2026, https://web.archive.org/web/20261024094000/https://cursor.com/docs/release-notes/origin.md, https://web.archive.org/web/20261024094330/https://cursor.com/docs/api/origin/reference/create-ruleset.md, https://downloads.cursor.com/co/2026.10.13-14-06-43-ea1dfe5/darwin-arm64/co.tar.gz, https://downloads.cursor.com/co/2026.10.23-18-47-36-f52be1e/darwin-arm64/co.tar.gz
- **Half:** capability | **Confidence:** medium

**What changed.** The ruleset editor's "Require review from code owners" toggle became a three-way Code owner review setting. Classic keeps the familiar rule: an owner must approve the files they own. Agentic still enforces CODEOWNERS, but when Origin's own agent reviews ownership on a pull request, its decision replaces the approval count. In the same week, an `ORIGIN_CODEOWNERS` entry can name an app as `app_<id>`, and that app's approval satisfies the paths it owns, provided it is installed on the repository's namespace; an uninstalled app shows "Not installed" and cannot approve. The notes do not say which changes the agent may clear without a person, which model decides, or where the decision is recorded. The shipped client protocol carries a risk rating, a per-rule human-review flag and bot owners, which points to a tiered design whose thresholds Cursor has not published.

**Operator consequence.** This is the window's clearest case of a human gate moving to a machine, and it is opt-in per ruleset. Before switching a protected branch to Agentic, list the paths where a named human owner is the accountability boundary and keep Classic there until Cursor documents when the agent's decision stands in for a person and how it is logged. Audit `ORIGIN_CODEOWNERS` for `app_` entries: an app's review scope now carries owner authority for its paths. If you trial Agentic, measure owner approvals avoided against agent decisions a human later overturned; that ratio, not the count of automated reviews, says whether scarce reviewer attention was saved.

## 2. Ruleset bypass now stays with the credential that holds it, must be requested explicitly from the CLI, and leaves a record

- **Date:** week of 2026-10-12 (web notes); 2026-10-16 (API); 2026-10-20 (Agents Window 3.26 notes); 2026-10-23 (CLI stable artifact)
- **Channel:** `mixed` (`docs-only` for hosted rules; `tagged-release` for `--bypass-rules` in Origin CLI stable artifact 2026.10.23-18-47-36-f52be1e)
- **Ancestry evidence:** Week-of-12-October notes: an app on a ruleset's bypass list can now push directly to a branch that blocks direct pushes when it uses its own installation token; an app pushing with a person's token no longer gets that person's bypass and has to open a pull request; a bypass merge now leaves an activity entry naming each skipped rule and an audit event. 2026-10-16 API entry: `originRole` bypass actors are rejected and omitted because a role actor never granted a bypass. Agents Window 3.26 notes (2026-10-20): the merge button stays disabled while an Origin rule blocks the merge, and bypassed merges show in the timeline. In the hash-checked bundles, the `--bypass-rules` option and the server refusal marker "would be skipped through your ruleset bypass" are absent from 2026.10.13-14-06-43-ea1dfe5 and present in 2026.10.23-18-47-36-f52be1e, whose `performChangeMerge` sends `bypassFailingRules` only when the flag is passed. The option's help text says a repository that requires it refuses a merge resting on the bypass until the flag is passed, and that it never passes a rule the caller cannot bypass. The public Merge Pull Request reference documents no such field.
- **Receipt:** https://web.archive.org/web/20261024092622/https://cursor.com/docs/release-notes/origin#oct-12-2026, https://web.archive.org/web/20261024092540/https://cursor.com/docs/api/origin/changelog#oct-16-2026, https://web.archive.org/web/20261024093142/https://cursor.com/docs/release-notes/agents-window#oct-20-2026, https://downloads.cursor.com/co/2026.10.13-14-06-43-ea1dfe5/darwin-arm64/co.tar.gz, https://downloads.cursor.com/co/2026.10.23-18-47-36-f52be1e/darwin-arm64/co.tar.gz
- **Half:** both | **Confidence:** high

**What changed.** Three moves point the same way. Bypass authority is bound to the credential that was granted it: an app's own installation token now carries the app's bypass for direct pushes, while a person's token used by an app no longer carries the person's. Bypass use becomes a deliberate act in the CLI (`origin pr merge --bypass-rules`, required where the repository demands it) instead of a side effect of who runs the merge. And every bypass merge is now itemized in the pull request activity and audit events, also visible in the Agents Window. The 16 October entry adds a defect disclosure in the restrictive direction: rulesets configured with role-based bypass actors never let anyone bypass, because Origin did not resolve role membership during evaluation.

**Operator consequence.** Re-audit direct pushes to protected branches made by apps acting as members before the week of 12 October; read with section 12, an app holding the user-token scope could have minted a token for a member on the bypass list, though the notes say nothing about whether that happened or how long the behavior lasted. Replace any `originRole` bypass entries with user, group or app entries and test the emergency path you thought you had. In automation, pass `--bypass-rules` only where a person decided to bypass, and review the "skipping N rules" entries. Making bypass explicit keeps a serial human decision at exactly the point where it is worth paying for.

## 3. Agent prompt steps in Origin CI can pass a required check by finishing neutral or skipped

- **Date:** week of 2026-10-12
- **Channel:** `docs-only` (hosted CI; no public `origin.ci.ts` reference)
- **Ancestry evidence:** Week-of-12-October notes: an Origin CI job or step may carry a `prompt` and optional `model`; a Cursor agent runs shell commands and reads, edits and searches files in the job workspace; it can mark the check neutral or skipped instead of passed or failed; neutral checks do not fail the overall CI status; prompt steps run as the team's Origin CI service account and need a team-owned namespace. The Create Ruleset reference says a required check run passes when it completes as success, neutral or skipped. The docs index lists no Origin CI page and `/docs/origin/ci.md` returns 404. Week-of-5-October notes added `agentEnvironment`, so CI jobs can boot from a Cloud Agent environment build.
- **Receipt:** https://web.archive.org/web/20261024092622/https://cursor.com/docs/release-notes/origin#oct-12-2026, https://web.archive.org/web/20261024094330/https://cursor.com/docs/api/origin/reference/create-ruleset.md, https://web.archive.org/web/20261024092622/https://cursor.com/docs/release-notes/origin#oct-5-2026
- **Half:** both | **Confidence:** medium

**What changed.** A general agent became a first-class CI step on Origin: write a prompt where a script would go and the agent does the work in the job's checkout. The agent also chooses the check's conclusion, and the documented required-check rule counts neutral and skipped as passing. An agent that decides a step does not apply therefore satisfies a required check exactly as a green test would. The step runs under a team service account, not the person who pushed, and the configuration language behind it is documented only through release notes.

**Operator consequence.** Do not make a prompt step's check required unless you accept an agent's neutral or skipped verdict as a pass; keep a deterministic check beside it for anything that gates a merge. Review what the Origin CI service account can write before giving it a prompt that edits files. Pin behavior with a test on a scratch repository, since neither the config reference nor the billing for prompt steps is published. This is a durable primitive, not a workaround: it lets a team delete glue scripts that called an agent from CI, and it moves human attention from writing CI steps to auditing what the agent declared not applicable.

## 4. Repository archives now obey the namespace IP allowlist for app and service-account callers; their git and API access still does not

- **Date:** 2026-10-22, 2026-10-23
- **Channel:** `docs-only`
- **Ancestry evidence:** Before/after reference text: in the 2026-10-14T20:42:55Z capture of the full reference the allowlist paragraph says the list does not restrict app JWTs, installation access tokens, installation user tokens or service accounts; in the 2026-10-24 capture the same paragraph adds "The exception is a repository archive", and the enforcement endpoint adds "except by Get Repo Tarball". API changelog 2026-10-22 (Breaking): Get Repo Tarball now answers every installation-token, installation-user-token and service-account request with a 302 whose signed URL works only from allowlisted addresses; it discloses that the first request for a commit used to stream the archive with 200, which an installation user token could do from any address. 2026-10-23 (Breaking): such tokens calling from outside the installation namespace's enforced list get 403.
- **Receipt:** https://web.archive.org/web/20261024092540/https://cursor.com/docs/api/origin/changelog#oct-22-2026, https://web.archive.org/web/20261024093747/https://cursor.com/docs/api/origin/reference/inbound-ip-allowlist.md, https://web.archive.org/web/20261024093815/https://cursor.com/docs/api/origin/reference/get-repo-tarball.md, https://web.archive.org/web/20261014204255/https://cursor.com/docs/api/origin/llms-full.txt, https://web.archive.org/web/20261024093701/https://cursor.com/docs/api/origin/llms-full.txt
- **Half:** both | **Confidence:** high

**What changed.** The inbound IP allowlist, which Origin applies to people's credentials since the week of 28 September, gained one exception for machine credentials: repository archives. App installation tokens, installation user tokens and service accounts must now call Get Repo Tarball from an allowlisted address, and the signed download URL they receive works only from listed addresses. Before 22 October, the first archive request for a commit streamed the whole tree inline, and an installation user token could do that from anywhere. Everything else stays as it was: git over HTTPS and the API accept app and service-account credentials from any address.

**Operator consequence.** If your namespace enforces an allowlist, deployment and CI apps that fetch archives from their own infrastructure (the marketplace lists Cloudflare, Netlify, Render, Spacelift and Vercel) will start getting 403; add their egress ranges or move them to a git fetch. Do not read the change as the allowlist now covering apps: classify each integration by credential, because a machine credential still reaches git and the API from any address. The pre-22-October archive gap is closed for archives only.

Current-state map, 2026-10-24:

- **What runs today:** stable 2026.10.23-18-47-36-f52be1e via `install.sh` (macOS, glibc Linux) or the undocumented `install.ps1` (native Windows x64); latest 2026.10.24-05-09-43-624e85d. Early beta product, Early Beta API with preview operations, MCP limited to Cursor and Grok Bot, CI config undocumented, several CLI command groups server-gated.
- **Default authority of an Origin app:** none until a workspace admin installs it; then the approved scopes over all or selected repositories, at most 15-minute installation tokens that can only narrow the grant, webhooks for subscribed events, and optionally acting as any member (section 12) or creating repositories with all-repository access (section 6). Apps work only on Origin-hosted repositories; on mirrored repositories only five read and sync scopes apply. Apps cannot request mirror-state, installation-management or app-management scopes. An admin narrows by approving fewer scopes, choosing selected repositories, pausing or uninstalling, and leaving apps off bypass lists. The IP allowlist is not an app boundary except for archives.
- **Default authority of a Cursor cloud agent:** per the docs, the user's Origin access; per the shipped CLI, a host-injected session scoped to repositories and scopes that cannot approve, request changes or dismiss reviews (section 13). Narrowed by repository grants, rulesets, the team's Origin switch and Projects approvals (week of 12 October: first use of a machine or environment needs a person's approval unless an admin auto-allows it, and a repository approval covers its Origin mirror).
- **Merge protections:** repository rulesets of kind `merge_branch`, `push_branch`, `push_tag` or `push_repository`, enforced `active`, `evaluate` or `disabled`, with rule types `pull_request` (approval count, code-owner review now Off, Classic or Agentic in the web editor, stale-review dismissal, last-push approval, thread resolution, allowed merge methods, required reviewer groups), `require_status_checks` (success, neutral or skipped pass), `require_branch_up_to_date`, `deletion`, `non_fast_forward`, `block_direct_updates`, `block_merges`, `ref_name_pattern`, `required_linear_history` and `max_file_size`; bypass actors are users, groups or apps, with `always` or `pull_request_only` modes. Request Changes from a writer blocks merge. Merges can pin the reviewed head (`expectedHeadSha`). Bypass merges are itemized, and unknown rule types and undeterminable code owners block (week of 28 September).

## Feature case

The question: does the Origin thread, Cursor moving from the editor to the place code is hosted, reviewed and merged, and what that does to the independent operating layer and to GitHub-shaped workflows, meet EDITORIAL.md's feature bar? Not this window. It meets two of the three conditions and fails the one that gives a feature its shape.

1. **The primary record can carry it: met.** This window alone produced 26 dated API changelog entries, before/after captures of the full reference and the OpenAPI file, a weekly note with defect disclosures, and two versioned CLI builds whose bundled code can be compared line by line. Few watchlist threads have a record this inspectable for a closed product.
2. **The people who matter decide or disagree in public, with receipts: not met.** Cursor decides in public through its docs: Agentic owner review, app code owners, archive allowlisting, explicit bypass. But no counterparty is on record. I found no GitHub statement, no marketplace partner dispute and no Cursor principal's post in the lanes I could check (web search, Hacker News search; the social logs were empty at read time). The only public voices are three Hacker News comments from users reacting to GitHub incidents, which are statements, not decisions, and not principals. A feature's "what was said, in order" section would be one-sided vendor documentation, and the dispute section would have nothing to settle.
3. **The consequence reaches operators of more than one tool, or changes a durable architecture question: met.** Origin relocates review and merge authority for teams that would otherwise run GitHub plus independent review, CI and security tools; it pulls those tools (CodeRabbit, Greptile, Semgrep, Socket, Buildkite, CircleCI and others) onto its own credential model; it keeps its agent interface closed to other harnesses for now; and Agentic owner review moves a human gate to Cursor's own agent.

Evidence that cuts against the easy "Cursor is eating the stack" story, which a feature would have to carry: Origin is still early beta with nine breaking API changes in ten days; its apps run only on Origin-hosted repositories while mirrored repositories keep CI and integrations on GitHub; its CLI ships two builds ahead of its notes and its CI language has no public reference; most cloud-agent and Bugbot changes this window still targeted GitHub (GitHub Enterprise `@cursor` comments, shared GitHub installations, OpenTelemetry commit logs for GitHub repositories only); the marketplace invites independent review and security vendors in rather than replacing them; and the IP allowlist still treats machine credentials as outside the people boundary. An independent operating layer that holds portable state and scoped authority still has a job here; Origin is building toward that job, not past it.

What a feature would have to establish that the record does not yet show: (a) Cursor's rule for when the Agentic decision replaces a human owner, and where it is logged, from Cursor's docs or a principal's statement; (b) whether approvals via Grok Bot and app code owners count toward required approvals, tested; (c) adoption beyond anecdote, such as vendor or partner figures on repositories hosted natively rather than mirrored; (d) a public position from GitHub, a marketplace partner or a practitioner who measured a migration, with receipts; (e) an export path for pull request history and reviews out of Origin, to match the import path that exists; (f) the cost of Origin CI prompt steps and storage. When (a) and (d) land, the thread likely clears the bar; until then it is a profile posture plus a weekly paragraph.
