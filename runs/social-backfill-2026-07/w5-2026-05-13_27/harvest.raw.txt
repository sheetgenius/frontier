VERBATIM_BEGIN
Five design principles for reviewing AI-written code

If you're running a multi-agent coding workflow, here are five I'd lift from /ph:pr-review — the code-review gate I built into Pilot House, my Claude Code plugin that wraps @doodlestein's Agent Flywheel:

1. Use multiple narrow reviewers, not one big one.
A general-purpose "review this code" prompt is too broad. Several narrow rubrics catch more in less time and run in parallel. Anthropic's pr-review-toolkit plugin gives you five — silent-failure-hunter, type-design-analyzer, pr-test-analyzer, comment-analyzer, code-reviewer — each with one lens.

2. Add an independent-model perspective.
Don't have one model review its own kind. Cross-model review catches blind spots. What Claude's rubric misses, GPT often catches, and vice versa. From inside Claude Code, /ph:ask-codex pipes the PR diff to Codex with a "find HIGH/CRITICAL only, independent perspective" template — different architecture, same diff, different findings.

3. Calibrate rigor by intent.
A POC needs a different review than production code. One global rubric either rubber-stamps everything or causes fixup spirals. Make rigor a property of the work, not the tool.

4. Bound iterative reviews to the delta.
When a review enters a fixup round, the next round should only see the new changes — not re-read the whole PR. Without this constraint, your loop will not converge.

5. Keep the human on the merge button.
Whatever you automate, the click that makes a change live should be a human's. That's not a workflow choice; it's an accountability choice.

If yours holds up better under real volume, I'd genuinely like to hear it.
VERBATIM_END
