- **Channel:** `tagged-release`

New docs page https://code.claude.com/docs/en/auto-mode-classifier-billing (fetched 2026-09-22): "Claude Code v2.1.278 or later asks the server to perform those checks as part of the session's own model requests, and doesn't charge for them when the server performs them"; when the server's checks cannot reach the session, "Claude Code holds the action and shows this notice at the prompt"; Enter continues on the billed local classifier, Esc cancels the held action; the usual cause is a gateway that strips the `safeguards` request field or drops `safeguard_results` from responses; "Pro, Max, and Team plans never show the notice"; in `-p` the text goes to stderr and stream-json emits a `system` warning; `CLAUDE_CODE_DISABLE_EXPERIMENTAL_BETAS=1` also turns server checks off; the variable "isn't read on a direct connection to the Anthropic API" and "is a temporary setting and may be removed in a later release". - **Receipt:** https://github.com/anthropics/claude-code/releases/tag/v2.1.278 and https://code.claude.com/docs/en/auto-mode-classifier-billing
- **Half:** both | security-relevant | **Confidence:** high

**What changed.** For API, Enterprise, Bedrock, Vertex, Foundry and gateway sessions, the auto-mode safety decision now happens on Anthropic's server inside the session's model request instead of in a separate client-side classifier call, and the classifier overhead is no longer billed. The default flipped twice in four days: 2.1.273 set local-by-default on the three cloud platforms; 2.1.278 set server-by-default everywhere the feature exists. Which classifier adjudicated a given action is now a per-session runtime fact that depends on platform and region rollout and on whether a gateway passes two undocumented-until-now fields through.

**Operator consequence.** Gateway operators: pass `safeguards` (request) and `safeguard_results` (response) through unchanged or set `CLAUDE_CODE_AUTO_MODE_SERVER=0` and keep paying for the local classifier; otherwise every auto-mode session holds its first checked action on a notice. Cost models that budgeted classifier tokens on API keys can drop them. The client-side control is temporary by the vendor's own statement; the server-side decision path has no documented rule list of its own, so item 8's rule names (`[Data Exfiltration]`) are the only inspection surface.

## 3. 2.1.248 and 2.1.259: two headless containment postures that refuse instead of asking

- **Date:** 2026-08-27 (`--restricted`) and 2026-09-02 (`--permission-prompts none`)
- **Channel:** `tagged-release`
- **Ancestry evidence:** changelog 2.1.248: "Added `--restricted` (or `CLAUDE_CODE_RESTRICTED=1`): removes the built-in tools that run commands or code and `WebFetch` (unless named in `--tools`), keeps file tools inside the working directory, refuses `bypassPermissions`, and ignores user, project and local settings files". CLI reference (https://code.claude.com/docs/en/cli-reference, fetched 2026-09-22): "loads only managed settings and `--settings`, refuses `bypassPermissions`, and refuses to create cloud sessions. Requires Claude Code v2.1.248 or later". What's New Week 35 (https://code.claude.com/docs/en/whats-new/2026-w35) documents it with "`--tools` is an allowlist, and its `default` preset doesn't restore the removed tools". Changelog 2.1.259: "Added `--permission-prompts none` for unattended headless hosts: anything that would prompt is denied automatically while the active permission mode (including auto mode) keeps deciding"; CLI reference: "Pass `none` when nobody can answer, and Claude Code denies them instead ... Requires Claude Code v2.1.259 or later". Related headless receipt repairs: 2.1.268 "Fixed `PermissionRequest` hooks not firing in `--print` mode"; 2.1.269 "Fixed `permission_denials` in `--output-format stream-json` results omitting Read, Edit and Write calls blocked by a path-scoped deny rule"; 2.1.277 "Fixed `claude -p` and Agent SDK sessions that could hang with no result after an internal error; they now report the error and exit with code 1".
- **Receipt:** https://github.com/anthropics/claude-code/releases/tag/v2.1.248 and https://github.com/anthropics/claude-code/releases/tag/v2.1.259
- **Half:** capability | **Confidence:** high

**What changed.** An eval harness on a shared machine can start Claude Code with no command execution, no WebFetch, no cloud sessions, file tools fenced to the working directory, and no user or project settings read at all. Separately, an unattended run can declare that nobody will answer prompts, so a would-be prompt becomes a deny rather than a stall or a fall-through to the SDK host. Three receipt gaps closed alongside: `PermissionRequest` hooks now fire under `--print` (they did not before 2.1.268), the stream-json `permission_denials` list is now complete for path-scoped denies, and an internal error is now an exit code 1 rather than a hang.

**Operator consequence.** Use `--restricted -p` for graders and untrusted-input review jobs; the `--tools` allowlist is the only way to give a removed tool back and the `default` preset does not. Use `--permission-prompts none` for cron and CI where a hook `ask` or an `ask` rule must fail closed; note that under auto mode the classifier still decides and the human never does. Adapters that parsed hangs as failures can now branch on exit 1; adapters that reconciled `permission_denials` against hooks were undercounting before 2.1.269.

## 4. 2.1.257: the September 1 authority batch

- **Date:** 2026-09-01
- **Channel:** `tagged-release`
- **Ancestry evidence:** changelog 2.1.257 (npm 2026-09-01T17:15:33Z). Settings doc (https://code.claude.com/docs/en/settings, fetched 2026-09-22): "`permissions.defaultMode` values `auto` and `bypassPermissions` don't take effect from project or local settings ... Before v2.1.257, `bypassPermissions` took effect from any file." Permission-modes doc: section "The first read outside the working directories" with "Requires Claude Code v2.1.257 or later" (absent from the 2026-08-18 Wayback capture at https://web.archive.org/web/20260818021849/https://code.claude.com/docs/en/permission-modes). Auto-mode-config doc: "Until this entry names that identity, the classifier blocks requests for the host's own credentials. Requires Claude Code v2.1.257 or later". What's New Week 36 (https://code.claude.com/docs/en/whats-new/2026-w36) summarizes the containment rule and the project-file `bypassPermissions` change.
- **Receipt:** https://github.com/anthropics/claude-code/releases/tag/v2.1.257
- **Half:** both | security-relevant | **Confidence:** high

**What changed.** In one release: (a) `defaultMode: "bypassPermissions"` in `.claude/settings.json` or `.claude/settings.local.json` is ignored, as `auto` has been since 2.1.207, so a repository can no longer put a clone into bypass mode; (b) auto mode gains a Containment Escape rule: cloud metadata-credential fetches, egress evasion and cross-tenant reach are no longer auto-approved unless the environment entry marks them expected; (c) auto mode prompts once before the first Read, Grep or Glob outside the working directories and offers `permissions.blockReadsOutsideWorkingDirectories`, which then fences file tools in every mode; (d) a `permissions.ask` rule was being skipped in auto mode when the matching command ran inside a compound command or subshell, so an ask rule was not a human checkpoint under auto mode before this build; (e) Bash `Read()`/`Edit()` deny rules did not apply to `< file` redirects or reader commands such as `tac` and `egrep`; (f) dismissing the Remote Control consent prompt with Esc or `n` counted as consent and the next request connected without asking; (g) `--disallowedTools` and session deny rules were dropped after the first settings reload when `allowManagedPermissionRulesOnly` was on; (h) plugins could read outside their own directory through a symlinked component path; (i) zsh `[[ ]]` conditionals that zsh parses differently from bash were auto-approved; (j) `/mcp` reconnect could connect a settings-file server that a managed allow/deny list loaded after startup should block; (k) Claude apps gateway sign-in now verifies the pinned TLS certificate; (l) reading an artifact that is not yours in Cowork or cloud sessions always asks, even in auto mode. Same release: Claude Fable 5.1 becomes the default Fable model (1M context, $10/$50 per Mtok, $0.25 cache reads), `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, network paths refused by `--add-dir`.

**Operator consequence.** Re-audit: any repo that committed `defaultMode: bypassPermissions` loses it on upgrade and must move it to user or managed settings or `--permission-mode`. Any auto-mode policy that relied on `permissions.ask` as the human checkpoint did not hold for `a && b` or `$(...)` forms before 2.1.257; re-test with a compound command. Any Remote Control host where someone dismissed the consent prompt on an older build may have accepted a connection without consent; check the claude.ai session list. Evals and cost models keyed on the `fable` alias moved to 5.1 on this build (gateway sessions keep Fable 5 until you pick 5.1 in `/model`). On stable, this batch arrived with the 09-15 hop.

## 6. Deny rules reached into Bash and retreated, twice

- **Date:** 2026-09-01 through 2026-09-16 (2.1.257, 2.1.259, 2.1.260, 2.1.268, 2.1.269, 2.1.271, 2.1.273, 2.1.274)

- **Ancestry evidence:** changelog 2.1.259: "Fixed Bash `Read()` deny rules not covering files given as option values (`--ignore-revs-file=.env`, `-f.env`, `@file`), `git diff`/`git grep` file operands, or `cd DIR && cat FILE` compounds; `grep -r`/`cp -r` over a directory holding a denied file now asks". Changelog 2.1.268: "Fixed deny and ask permission rules on symlinked directories (`/etc`, `/tmp`, `/var` on macOS; `/bin` on Linux) not applying when a path was given by its real location, and Bash commands ignoring deny rules written on a symlinked path spelling" and "Fixed a case where a Read or Edit deny rule did not apply when an `env -C`, `eval` or similar command the permission checker cannot analyze was on the same line". Changelog 2.1.269: "Fixed `Edit()` deny rules and the write-path check not applying to the file a Bash `tee` command writes; a `Bash(tee:*)` allow rule no longer covers destinations outside the working directories" and "Fixed a deny or ask permission rule starting with `!` applying beyond the settings source that wrote it". Changelog 2.1.271: "Fixed Bash permission checks skipping files a wildcard expands to when the wildcard sits in a command's pattern or option value", "missing the file that `fmt`, `column` and similar commands read when it follows an option the checker doesn't recognize", "shell variable declaration flags cannot misrepresent the command being run", "Bash commands with two directory changes, a subshell, or a `cd`+`git` chain skipping the prompt under `permissions.blockReadsOutsideWorkingDirectories` in bypass and auto mode". Changelog 2.1.273: "Reverted a 2.1.268 change that checked Read and Edit deny rules on Bash lines the permission checker can't analyze (`eval`, `env -C`); commands like `time -p make build` prompt again instead of being denied" and "Fixed Bash commands the permission checker cannot fully analyze skipping the prompt under `permissions.blockReadsOutsideWorkingDirectories`, and a subshell hiding a dangerous `rm` in bypass mode". Changelog 2.1.274: "Fixed Bash permission checks for commands that loop over or assign certain special shell variables; these commands now ask" and "worktree-isolated sessions accepting Bash commands with certain nested shell expansions; these are now refused". Changelog 2.1.270 is a one-line hotfix: "read-only git commands in Bash unexpectedly asking for permission after a session had been running for a while (regression in 2.1.269)".
- **Receipt:** https://github.com/anthropics/claude-code/releases/tag/v2.1.260 and https://github.com/anthropics/claude-code/releases/tag/v2.1.273
- **Half:** defect | security-relevant | **Confidence:** high

**What changed.** The vendor extended `Read()` deny enforcement to Bash arguments on 09-02 and reverted it on 09-03 because it broke `npm run build`; extended it to unanalyzable Bash lines on 09-10 and reverted that on 09-15 because it denied `time -p make build`. Between and around those, seven other ways a written deny rule did not bind were closed: parentheses in a rule path made the rule invalid and the folder writable; one bad pattern disabled every file edit; `/tmp` and `/etc` rules did not match their real paths; `tee` wrote past `Edit()` deny; wildcards and unrecognized options hid the file; a `!`-prefixed rule leaked across settings sources; and `cd`/subshell chains skipped `blockReadsOutsideWorkingDirectories` in bypass and auto mode.

**Operator consequence.** At 2.1.278 a `Read(...)` deny binds on the file tools, on Grep and Glob including symlinked search paths, on Bash `< file` redirects and recognized reader commands, on `tee` targets, on wildcard expansions, and on symlinked directory spellings. It does not bind on Bash lines the checker cannot analyze (`eval`, `env -C`, `time -p`): those prompt. It does not bind on arbitrary Bash arguments: that extension was reverted. If a deny rule exists to keep `.env` out of a shell, run `cat < .env`, `tac .env`, `tee .env`, `eval "cat .env"` and `time cat .env` on your build and record which prompt, deny or run; expect different answers on stable (2.1.267: 2.1.257 and the 2.1.260 revert applied, nothing from 2.1.268 onward) and latest. The 2.1.270 hotfix means 2.1.269 prompted on read-only git in long sessions; if a fleet pinned 2.1.269, that is why.
